### 유휴 연결 시간 (keep-alive)

- Pod uvicorn 의 유휴 연결 시간을 5 s 에서 75 s 로 늘렸다(같은 Pod, 같은 부하) [실험 결과].
  - 30초 간격에서도 연결을 이어 쓰게 됐다.
  - 전송 등 중앙값은 4.41 → 3.56 s, 처리 중앙값은 9.09 → 8.22 s(−0.88 s, −9.6 %)로 줄었다 [계산].
- 이 결과는 2차 7절의 가설(새 연결의 비용)을 지지한다.
- 빈 큐 슬롯 S0 는 10.5 → 9.0 s 로 줄었다 [계산]. 2차 S0 는 11.5 s 였다.

### 스레드 8

- Pod 컨테이너의 CPU 한도는 100 ms 주기마다 7.65 코어다(cgroup v1). 기본 스레드에서는 한도에 걸린 주기가 G0 에서 0.5~0.7 %, G2r 에서 2.2 % 였다 [계산].
  - 걸린 주기마다 CPU 여러 개가 함께 멈췄다(CPU 를 합친 멈춘 시간이 주기마다 약 1.7~2.2 s).
- 스레드 8 에서는 한도에 걸린 주기가 0 이었다 [실험 결과].
- 추론 시간은 크게 줄지 않았다: 중앙값 −2.6 %, 평균 −0.6 % [계산].
- G2r·F 는 기본 스레드로 돌렸다.

### 슬롯 2개 (G2r)

- 처리량은 늘었지만 2배는 아니다.
  - `MODEL_LOCK` 이 잡혀 있던 시간은 56.8 %, GPU 사용률 평균은 32.6 % 였다.
  - 늘어난 처리 시간(중앙값 8.22 → 13.03 s)의 대부분은 변환 뒤 응답·내려받기다 [계산].
  - 이 구간은 1.90 s 에서, 잠금을 기다리지 않은 작업은 6.69 s, 기다린 작업은 4.33 s(중앙값)로 길어졌다.
  - 기다린 작업의 이 구간은 다른 작업의 추론과 거의 겹치지 않았고(중앙값 0 %, 90건 중 80건은 겹침 없음), 다른 작업의 응답·내려받기와 겹쳤다(중앙값 65 %).
- 원인 후보는 동시에 나가는 응답·내려받기가 Pod 의 보내는 경로를 나눠 쓰고, 다른 작업의 추론·변환과도 CPU 를 다투는 것이다 [가설]. CPU 한도(걸린 주기 2.2 %)는 주된 원인이 아니다 [계산].
- 이 λ(실제 564건/h)에서는 슬롯 2개도 넘쳤다. 시스템 안 작업은 최대 24건까지 늘었다.

### 추론 서비스가 죽었을 때 (F2-real)

- 잃은 작업은 0 이었다(마지막 시도 기준) [실험 결과].
- 그 순간 처리 중이던 1건은 0.18 s 뒤 `INFERENCE_UNAVAILABLE` 로 FAILED 가 됐다. k6 가 retry 해서 COMPLETED 가 됐다.
  - backend 는 이 1건을 스스로 다시 하지 않는다.
  - 앱이 retry 하지 않으면 이 1건은 실패로 남는다.
- 나머지 작업은 오프라인 대기로 PENDING 에서 기다렸다가 처리됐다.

### 타임아웃이 처리보다 짧을 때 (F1b-real)

- 모든 시도가 실패했다. 그런데도 Pod 는 버려진 추론을 적어도 61번 끝까지 돌렸다 [실험 결과].
- 그 뒤의 변환이 정리 `DELETE` 가 지운 작업 폴더를 다시 만들어(`convert_asset.py` 의 `os.makedirs`) 폴더 3개를 남겼다.
- 연결 오류에만 다시 보내는 정리 재시도(PR #8, 2026-11-19 main 병합)로는 이것을 막지 못한다.
  - 이때 `DELETE` 는 204·500 으로 답했기 때문이다.
  - 고칠 곳은 추론 서비스다. PR #11 로 고쳤다(2026-11-19 main 병합) [구현됨]. Pod 에서 다시 잰 기록은 없다 [계획].

### 경로 끊김

- VM ↔ Pod 경로가 계획 밖에서 두 번 끊겼다: 16:38 의 약 83 s 와 16:59 의 49.6 s [실험 결과].
- VM 의 tailscaled 로그에는 같은 때 연결 열기 시간 초과와 DERP·제어 서버 연결 재설정이 있다.
- backend 오프라인 대기 덕분에 잃은 작업은 없었다.
- 두 번 모두 운영의 끊김 알림 유예 45 s 보다 길었다. 운영이었다면 알림이 갔을 것이다 [계산].

### VM CPU

- 작업 하나에 4.0~4.8 코어·초가 들었다 [계산]. 가장 많은 작업을 돈 G2r 의 4.04 로 계산하면 2 vCPU 의 70 % 상한은 약 1,250건/h 다. 2차의 약 1,340건/h 와 비슷하다.

## 2. G0 — 유휴 연결 시간과 스레드 [실험 결과·계산]

같은 Pod 에서 `smoke.js` 로 30초마다 흐름 1개를 15분씩 세 번 돌렸다. 실행 사이에 추론 서비스 설정 하나만 바꿨다. 아래 값은 경로 끊김(8절)에 걸리지 않은 작업만 쓴 것이다.
- '깨끗한' 작업의 기준: `queuedMs` < 10 s, `processingMs` < 20 s.
- `g0ka5` 에서는 2건을 뺐다: 대기 87.2·35.8 s.
- `g0ka75` 에서도 2건을 뺐다: 처리 71.5 s, 대기 13.4 s.
