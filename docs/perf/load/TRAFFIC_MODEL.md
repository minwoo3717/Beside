# 목표 트래픽 모델 — 쏘카 수준(T3)과 합격 기준

작성 2026-11-01, 브랜치 `load/socar`(W1 B0). 멘토링 논의 사항("쏘카 수준 트래픽을 목표로 설정하고 테스트")과 교수님 피드백("부하·장애 테스트도 배포 환경에서")을 숫자로 옮긴 문서다. 2026-11-01 전에는 이 목표가 리포 어디에도 기록돼 있지 않았다.

표기:
- **[가정]** 우리가 정한 비율·크기. 바꿀 수 있다.
- **[파생]** [가정]과 공식으로 계산한 값. 가정이 바뀌면 다시 계산한다.
- **[제안값]** 계약 회의에서 정하기 전의 합격 기준·상한.
- **[계획]** 아직 하지 않은 시험. **이 문서에는 부하 시험 측정값이 하나도 없다.** 루프백 벤치마크를 인용하는 곳만 [실험 결과]로 적는다.

- 같은 숫자는 `python scripts/load/model.py` 로 다시 만든다(같은 브랜치의 부하 스크립트 조각, [scripts/load/](../../../scripts/load/)). 이 문서와 출력이 다르면 공식과 가정을 다시 확인해 둘을 맞춘다.
- **작업 1건의 생성 시간 T 는 아직 재지 않았다.** exp-01(3D 담당, GPU PC)이 없어 T 를 30·60·120·300초로 바꿔 가며 계산하고, 표의 기본값은 60초다. exp-01 이 나오면 그 T 로 이 문서의 표를 모두 다시 계산한다(12절).

## 요약

발표 한 문장: "API 계층은 쏘카 규모(T3) 요청률로 **측정**했다. 생성은 GPU 1대가 시간당 3600/T건이라 T3에는 N대가 필요하다(**계산**). 우리는 1대이므로 넘치는 요청을 큐 상한으로 즉시 거절한다(**측정**)." — 지금은 세 부분 모두 [계획]이다.

- **API 계층**: T3 평상시 약 37 RPS, 최악(스파이크 + GPU 포화) 약 920 RPS 를 VM 에서 버텨야 한다 [파생]. A 시리즈로 잰다 [계획].
- **GPU 계층**: GPU 1대는 시간당 3600/T건이다. T2부터 1대로는 모자라고(T ≤ 21초여야 함), T3는 T=60초면 86대가 필요하다 [파생]. 우리는 1대이므로 큐 상한으로 즉시 거절하고(안건 #19), G 시리즈로 큐 이론을 검증한다 [계획].
- **디스크**: T2(하루 2.3 GB)에서도 VM 디스크가 찬다: 사용 가능 약 20 GB [가정] 기준 약 9일 (30 GB 전부면 13일) [파생]. 보존 정책이 필요하다(안건 #21).

- **GPU 갖춤**: 이용률 ρ ≤ 0.7 이 되게 GPU 를 둔 경우다(c = ⌈λT/0.7⌉ → T1 1대, T2 3대, T3 86대, 스파이크 258대). 큐 대기 Wq 는 M/M/c 로 넣었다(T1 12초, T2 26.7초, T3·스파이크 약 0초).
- **GPU 포화**: GPU 가 모자라 대기열이 앱 최대 대기(600초)까지 찬 경우다. 기다리는 앱이 모두 600초 동안 폴링하므로 폴링이 300·λ 에서 멈춘다.
- 송신·수신은 피크 1시간의 평균이다. 순간 값은 이보다 크다.

| 요청 | 계산 | RPS |
|---|---|---|
| 폴링 `GET /api/v1/jobs/{id}` | L = λ(Wq + T) = 1.0 × (약 0 + 60) = 60 → L/2 | 30 |
| `GET /api/v1/healthz` | 동시 1,800 ÷ 세션 360초 | 5 |
| `POST /api/v1/jobs` | λ | 1 |
| `GET .../asset` | 0.95·λ | 0.95 |
| `POST .../retry` | 0.05·λ | 0.05 |
| 합계 | | 약 37 |

- GPU 가 포화되면 폴링이 300·λ = 300 이 되어 약 307 RPS 다.
- 스파이크(λ = 3.0, 동시 5,400)에 GPU 포화가 겹치면 900 + 15 + 3 + 2.85 + 0.15 = 약 921 RPS 다(요약의 "약 920").
- T2 의 1.6 RPS: c=3, Wq = 26.7초(M/M/3) → L = 0.033 × 86.7 = 2.9 → 폴링 1.44 + 나머지 0.13.

## 4. 공식

- 시스템 안의 작업 수(리틀의 법칙): **L = λ·(Wq + T)**. λ 는 생성 요청률(건/초), Wq 는 큐 대기, T 는 생성 시간이다.
- 폴링 RPS = **L / 2** (앱마다 2초에 1회).
- 폴링 상한: 앱이 600초에 포기하므로 L ≤ 600·λ → 폴링 ≤ **300·λ**.
- 전체 RPS = L/2 + 동시 사용자/360 + λ(생성) + 0.95·λ(에셋) + 0.05·λ(retry).
- GPU 1대 용량 = **3600/T 건/h**. 이용률 ρ ≤ 0.7 을 지키면 **2520/T 건/h**.
- 필요 GPU 수 **c = ⌈λ·T / 0.7⌉**.
- 큐 대기: M/M/c(Erlang C)로 계산한다. 생성 시간이 거의 일정하므로 실제 대기는 M/D/c 쪽(대략 절반)이고, 이 문서의 값은 상한이다. 예: c=1, T=60, ρ=0.7 이면 M/M/1 Wq = 140초, M/D/1 Wq = 70초.
- **큐 상한** [제안값]: **Q_max = ⌊c·(600 − T)/T⌋**. 앞에 Q건이 기다리면 내 작업은 약 (Q/c + 1)·T 뒤에 끝난다. Q 가 이 값을 넘는 자리에 서면 어차피 앱이 600초에 포기하므로, 작업을 만들지 않고 즉시 503 으로 거절한다(안건 #19). 지금 구성(c=1, T=60)이면 **9건**이다.
- **GPU 증설·감축 기준** [제안값]: 추정 이용률 λ̂·T̂/c > 0.7 이 10분 지속되거나 p95 `queuedMs` > 60초이면 늘린다. 0.4 미만이 30분 지속되면 줄인다. λ̂ 는 최근 10분의 생성 요청률, T̂ 는 최근 `processingMs` 의 중앙값이다.
- 단순화: retry 로 다시 도는 5 %는 GPU 계산에서 뺐다. 넣으면 필요 GPU 가 약 5 % 늘어난다(T3·T=60 에서 86 → 약 90대).

## 5. GPU 계층 [파생]

| T [가정] | GPU 1대 용량 | 1대 (ρ ≤ 0.7) | T2 필요 GPU | T3 필요 GPU (ρ ≤ 0.7) | Q_max (c=1) |
|---|---|---|---|---|---|
| 30초 | 120건/h | 84건/h | 2 | 43 (42.9) | 19 |
| 60초 | 60건/h | 42건/h | 3 | 86 (85.7) | 9 |
| 120초 | 30건/h | 21건/h | 6 | 172 (171.4) | 4 |
| 300초 | 12건/h | 8.4건/h | 15 | 429 (428.6) | 1 |

- T2 를 1대로 처리하려면 2520/T ≥ 120 → **T ≤ 21초**.
- T3 스파이크(λ = 3.0/s)를 T=60 으로 받으려면 258대가 필요하다.
- 우리 구성은 GPU 1대(`inference.max-concurrency=1`)다. T2 이상에서 넘치는 요청은 큐 상한으로 즉시 거절하는 것이 맞는 동작이고, 늘리는 방법(다중 GPU 풀, W2 B9)은 [계획]이다.

## 6. API 계층과 GPU 계층

- API 계층(Spring + H2 + Caddy)은 생성 시간과 상관없이 요청 수만 감당하면 된다. 평상시 37 RPS 는 작지만, GPU 가 포화되면 기다리는 모든 앱이 폴링하므로 307 RPS, 스파이크까지 겹치면 921 RPS 로 뛴다. **GPU 가 모자랄수록 API 부하가 커진다.**
- 그래서 큐 상한은 GPU 와 함께 API 도 보호한다. 상한이 있으면 L ≤ c + Q_max 라서 폴링 ≤ (c + Q_max)/2 다. c=1, Q_max=9 이면 5 RPS 수준이다(거절된 사용자가 Retry-After 를 지킨다고 볼 때).
- 참고 [실험 결과]: 개발 PC 루프백(127.0.0.1, 서버를 논리 CPU 2개에 고정, TLS·프록시 없음)에서 현재 버전(v1)의 COMPLETED 작업 폴링 처리량은 3회 1,744~1,834 req/s, 중앙값 1,792 req/s 다(2026-11-01, `docs/perf/data/2026-11-01_1257`, `bench.pollReqPerSec`). 921 RPS 의 약 두 배지만 VM(2 vCPU·4 GB) + Caddy TLS + 인터넷 경로에서는 다를 수 있으므로 VM 에서 다시 잰다(A2). 이 값을 VM 용량으로 인용하지 않는다.

## 7. 디스크

- 작업마다 2.3 MB 가 쌓인다. main 에는 완료된 작업의 사진·GLB 를 지우는 코드가 없다.
- T2: 2.3 GB/일. VM 디스크 30 GB 중 OS·Docker 이미지·로그·H2 백업을 빼면 **사용 가능 약 20 GB [가정] 기준 약 9일 (30 GB 전부면 13일)** 이면 찬다. `model.py` 가 내는 값은 30 GB 기준인 13일이다(`tiers.json` 의 `diskBudgetGB` 30). 9일은 위 20 GB 가정으로 나눈 값이다.
- T3: 69 GB/일. VM 디스크 하나로는 하루도 버티지 못하므로 오브젝트 스토리지가 필요하다(설계 문서 `docs/SCALE.md` [계획]).
- 공개 전에 업로드·GLB 보존 정책이 필요하다(안건 #21). 부하 시험은 별도 볼륨(`beside-loadtest-storage`)에 쓰고, 중단 조건에 디스크 80 %를 둔다.

## 8. 합격 기준 [제안값 — 계약 회의 전]

RTT_base 는 A0(연기 시험)에서 잰 healthz p50 이다. 네트워크 왕복은 빼고 서버·프록시의 몫만 기준으로 삼기 위해서다.

| 엔드포인트 | p95 | p99 |
|---|---|---|
| healthz | RTT_base + 50 ms | RTT_base + 150 ms |
| `GET /jobs/{id}` | RTT_base + 100 ms | RTT_base + 300 ms |
| `POST /jobs` (0.8 MB) | 1.5 s (서버 `uploadMs` p95 ≤ 300 ms) | 3 s |
| `GET asset` (1.5 MB) | 첫 바이트 RTT_base + 150 ms, 전체 3 s | 전체 6 s |

공통 기준:
- 5xx·연결 오류 < 0.5 %. 의도한 4xx·429·503 은 따로 센다.
- 600초를 넘긴 흐름 0건, 완료 처리량 ≥ 들어온 양의 95 %.
- VM CPU 단계 평균 < 85 %, GC 뒤 힙 < 75 %.

- **깨지는 지점**: 유지 구간에서 위 기준을 처음 넘는 단계다. 보고하는 용량은 마지막으로 통과한 단계, 운영 상한은 그 70 %로 둔다.
- **중단 조건**: 오류 > 5 %가 1분 지속되거나 디스크 > 80 %이면 그 자리에서 멈추고 기본 스택으로 복구한다.

## 9. 시험 구성 [계획]

보고용 수치는 배포 VM(2 vCPU·4 GB·30 GB)에서 잰다. 이 PC 에는 Docker·k6 가 없고, 로컬 실행은 스크립트가 동작하는지만 보며 결과로 쓰지 않는다.

- **격리**: `deploy/docker-compose.loadtest.yml` 덮어쓰기 파일로 backend 서비스만 바꾼다(볼륨 `beside-loadtest-storage`, 웹훅·H2 백업 끔, `METRICS_ENV=loadtest`). - **A 시리즈(API 계층)**: `mock,prod`, PENDING 0초·PROCESSING 60초, @Async 풀 400. 기본 풀은 8스레드라 늘리지 않으면 mock 이 "GPU 8대"처럼 동작한다. 합성 GLB 1.5 MB 를 볼륨에 미리 넣는다(리포의 `sample-dog.glb` 는 0 B).
- **G 시리즈(GPU 큐)**: `real,prod` + 추론 스텁(패스스루, 업로드 모드, Tailscale). 스텁의 `BESIDE_PASSTHROUGH_DELAY_MS`·`_JITTER_MS`·`_SLOTS`·`_FAIL_RATE`·`_FAIL_TOKEN`·`_SLOW_TOKEN`/`_SLOW_MS` 로 생성 시간·실패·GPU 수를 흉내 낸다. 실제 GPU PC 는 쓰지 않는다.

## 10. 정직성 규칙

- 루프백 결과는 버전 비교에만 쓴다. mock 결과는 "생성을 뺀 API 처리량", 스텁 결과는 "큐 동작 검증(생성 시간은 가정 T)"이라고 적는다.
- k6 VU 수는 동시 사용자 수가 아니다. 사용자 수는 도착률로 환산해 적는다.
- "API 계층이 T3를 통과했다"는 다음을 모두 만족할 때만 쓴다: T3 요청률 10분 유지, `dropped_iterations` 0, 8절 기준 충족, 클라이언트 CPU < 70 %, 업링크 비포화. 못 넘으면 "최대 지속 처리량 Y RPS(T3의 k %)"로 쓴다.
- 결과는 [실험 결과]로 적고 조건(VM 사양, 커밋 SHA, k6 버전, 업링크, 사진 크기)을 붙인다.
- VM·k6·Docker 에서 실제로 돌리기 전에는 이 문서의 어떤 값도 측정값처럼 쓰지 않는다.

## 11. 이름

- k6 쪽 값은 `load.` 접두사를 쓴다(k6 는 이름에 점을 못 써서 `load_postMs` 처럼 밑줄로 적는다). `bench.*` 처럼 `docs/perf` 전용이고 [METRICS.md](../../METRICS.md) 에 등록하지 않는다(안건 [#15](../../api/REVIEW_CHECKLIST.md)).
- 서버 운영 지표 `beside.*`(Micrometer, Prometheus 이름은 `beside_jobs_finished_total` 등)는 METRICS 에 추가로 적는다(같은 브랜치의 Java 조각).
- 서버 값 `uploadMs`·`queuedMs`·`processingMs`·`totalMs` 는 METRICS §1 의 뜻 그대로 쓴다.

## 12. 데이터 위치와 다시 계산

- 원시 결과: `docs/perf/load/data/<YYYY-MM-DD_HHMM>/run.json` + k6 summary·Prometheus 구간 CSV 등. k6 스크립트와 수집 도구는 [scripts/load/](../../../scripts/load/).
- 부하 문서는 `docs/perf/notes/` 에 넣지 않는다. `scripts/perf/report.py` 가 그 폴더의 모든 `.md` 를 루프백 보고서 PDF 에 넣기 때문이다.
- exp-01 의 T 가 나오면: `scripts/load/model.py` 에 그 T 를 넣는다 → 3·5절 표와 Q_max 를 다시 계산한다 → 안건 #19 의 상한 제안값을 고친다 → G 시리즈 스텁 지연을 그 T 로 바꿔 다시 잰다.
