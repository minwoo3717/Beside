# 목표 트래픽 모델 — 쏘카 수준(T3)과 합격 기준

작성 2026-11-01, 브랜치 `load/socar`(W1 B0). 멘토링 논의 사항("쏘카 수준 트래픽을 목표로 설정하고 테스트")과 교수님 피드백("부하·장애 테스트도 배포 환경에서")을 숫자로 옮긴 문서다. 2026-11-01 전에는 이 목표가 리포 어디에도 기록돼 있지 않았다.

표기:
- **[가정]** 우리가 정한 비율·크기. 바꿀 수 있다.
- **[파생]** [가정]과 공식으로 계산한 값. 가정이 바뀌면 다시 계산한다.
- **[제안값]** 계약 회의에서 정하기 전의 합격 기준·상한.
- **[계획]** 아직 하지 않은 시험. **이 문서에는 부하 시험 측정값이 하나도 없다.** 루프백 벤치마크를 인용하는 곳만 [실험 결과]로 적는다.

- 같은 숫자는 `python scripts/load/model.py` 로 다시 만든다(같은 브랜치의 부하 스크립트 조각, [scripts/load/](../../../scripts/load/)). 이 문서와 출력이 다르면 공식과 가정을 다시 확인해 둘을 맞춘다.
- **작업 1건의 생성 시간 T 는 아직 재지 않았다.** exp-01(3D 담당, GPU PC)이 없어 T 를 30·60·120·300초로 바꿔 가며 계산하고, 표의 기본값은 60초다. exp-01 이 나오면 그 T 로 이 문서의 표를 모두 다시 계산한다(12절).

## 요약

발표 한 문장: "API 계층은 쏘카 규모(T3) 요청률로 **측정**했다. 생성은 GPU 1대가 시간당 3600/T건이라 T3에는 N대가 필요하다(**계산**). 우리는 1대이므로 넘치는 요청을 큐 상한으로 즉시 거절한다(**측정**)." — 지금은 세 부분 모두 [계획]이다.

- **API 계층**: T3 평상시 약 37 RPS, 최악(스파이크 + GPU 포화) 약 920 RPS 를 VM 에서 버텨야 한다 [파생]. A 시리즈로 잰다 [계획].
- **GPU 계층**: GPU 1대는 시간당 3600/T건이다. T2부터 1대로는 모자라고(T ≤ 21초여야 함), T3는 T=60초면 86대가 필요하다 [파생]. 우리는 1대이므로 큐 상한으로 즉시 거절하고(안건 #19), G 시리즈로 큐 이론을 검증한다 [계획].
- **디스크**: T2(하루 2.3 GB)에서도 VM 디스크가 찬다: 사용 가능 약 20 GB [가정] 기준 약 9일 (30 GB 전부면 13일) [파생]. 보존 정책이 필요하다(안건 #21).

- **GPU 갖춤**: 이용률 ρ ≤ 0.7 이 되게 GPU 를 둔 경우다(c = ⌈λT/0.7⌉ → T1 1대, T2 3대, T3 86대, 스파이크 258대). 큐 대기 Wq 는 M/M/c 로 넣었다(T1 12초, T2 26.7초, T3·스파이크 약 0초).
- **GPU 포화**: GPU 가 모자라 대기열이 앱 최대 대기(600초)까지 찬 경우다. 기다리는 앱이 모두 600초 동안 폴링하므로 폴링이 300·λ 에서 멈춘다.
- 송신·수신은 피크 1시간의 평균이다. 순간 값은 이보다 크다.

| 요청 | 계산 | RPS |
|---|---|---|
| 폴링 `GET /api/v1/jobs/{id}` | L = λ(Wq + T) = 1.0 × (약 0 + 60) = 60 → L/2 | 30 |
| `GET /api/v1/healthz` | 동시 1,800 ÷ 세션 360초 | 5 |

| `POST .../retry` | 0.05·λ | 0.05 |
| 합계 | | 약 37 |

- GPU 가 포화되면 폴링이 300·λ = 300 이 되어 약 307 RPS 다.
- 스파이크(λ = 3.0, 동시 5,400)에 GPU 포화가 겹치면 900 + 15 + 3 + 2.85 + 0.15 = 약 921 RPS 다(요약의 "약 920").
- T2 의 1.6 RPS: c=3, Wq = 26.7초(M/M/3) → L = 0.033 × 86.7 = 2.9 → 폴링 1.44 + 나머지 0.13.

## 4. 공식

- 시스템 안의 작업 수(리틀의 법칙): **L = λ·(Wq + T)**. λ 는 생성 요청률(건/초), Wq 는 큐 대기, T 는 생성 시간이다.
- 폴링 RPS = **L / 2** (앱마다 2초에 1회).
- 폴링 상한: 앱이 600초에 포기하므로 L ≤ 600·λ → 폴링 ≤ **300·λ**.
- 전체 RPS = L/2 + 동시 사용자/360 + λ(생성) + 0.95·λ(에셋) + 0.05·λ(retry).
- GPU 1대 용량 = **3600/T 건/h**. 이용률 ρ ≤ 0.7 을 지키면 **2520/T 건/h**.
- 필요 GPU 수 **c = ⌈λ·T / 0.7⌉**.
- 큐 대기: M/M/c(Erlang C)로 계산한다. 생성 시간이 거의 일정하므로 실제 대기는 M/D/c 쪽(대략 절반)이고, 이 문서의 값은 상한이다. 예: c=1, T=60, ρ=0.7 이면 M/M/1 Wq = 140초, M/D/1 Wq = 70초.
- **큐 상한** [제안값]: **Q_max = ⌊c·(600 − T)/T⌋**. 앞에 Q건이 기다리면 내 작업은 약 (Q/c + 1)·T 뒤에 끝난다. Q 가 이 값을 넘는 자리에 서면 어차피 앱이 600초에 포기하므로, 작업을 만들지 않고 즉시 503 으로 거절한다(안건 #19). 지금 구성(c=1, T=60)이면 **9건**이다.
- **GPU 증설·감축 기준** [제안값]: 추정 이용률 λ̂·T̂/c > 0.7 이 10분 지속되거나 p95 `queuedMs` > 60초이면 늘린다. 0.4 미만이 30분 지속되면 줄인다. λ̂ 는 최근 10분의 생성 요청률, T̂ 는 최근 `processingMs` 의 중앙값이다.
- 단순화: retry 로 다시 도는 5 %는 GPU 계산에서 뺐다. 넣으면 필요 GPU 가 약 5 % 늘어난다(T3·T=60 에서 86 → 약 90대).

## 5. GPU 계층 [파생]

| T [가정] | GPU 1대 용량 | 1대 (ρ ≤ 0.7) | T2 필요 GPU | T3 필요 GPU (ρ ≤ 0.7) | Q_max (c=1) |
|---|---|---|---|---|---|
| 30초 | 120건/h | 84건/h | 2 | 43 (42.9) | 19 |
| 60초 | 60건/h | 42건/h | 3 | 86 (85.7) | 9 |
| 120초 | 30건/h | 21건/h | 6 | 172 (171.4) | 4 |
| 300초 | 12건/h | 8.4건/h | 15 | 429 (428.6) | 1 |

- T2 를 1대로 처리하려면 2520/T ≥ 120 → **T ≤ 21초**.
- T3 스파이크(λ = 3.0/s)를 T=60 으로 받으려면 258대가 필요하다.
- 우리 구성은 GPU 1대(`inference.max-concurrency=1`)다. T2 이상에서 넘치는 요청은 큐 상한으로 즉시 거절하는 것이 맞는 동작이고, 늘리는 방법(다중 GPU 풀, W2 B9)은 [계획]이다.

## 6. API 계층과 GPU 계층

- API 계층(Spring + H2 + Caddy)은 생성 시간과 상관없이 요청 수만 감당하면 된다. 평상시 37 RPS 는 작지만, GPU 가 포화되면 기다리는 모든 앱이 폴링하므로 307 RPS, 스파이크까지 겹치면 921 RPS 로 뛴다. **GPU 가 모자랄수록 API 부하가 커진다.**
- 그래서 큐 상한은 GPU 와 함께 API 도 보호한다. 상한이 있으면 L ≤ c + Q_max 라서 폴링 ≤ (c + Q_max)/2 다. c=1, Q_max=9 이면 5 RPS 수준이다(거절된 사용자가 Retry-After 를 지킨다고 볼 때).
- 참고 [실험 결과]: 개발 PC 루프백(127.0.0.1, 서버를 논리 CPU 2개에 고정, TLS·프록시 없음)에서 현재 버전(v1)의 COMPLETED 작업 폴링 처리량은 3회 1,744~1,834 req/s, 중앙값 1,792 req/s 다(2026-11-01, `docs/perf/data/2026-11-01_1257`, `bench.pollReqPerSec`). 921 RPS 의 약 두 배지만 VM(2 vCPU·4 GB) + Caddy TLS + 인터넷 경로에서는 다를 수 있으므로 VM 에서 다시 잰다(A2). 이 값을 VM 용량으로 인용하지 않는다.

## 7. 디스크

- 작업마다 2.3 MB 가 쌓인다. main 에는 완료된 작업의 사진·GLB 를 지우는 코드가 없다.
- T2: 2.3 GB/일. VM 디스크 30 GB 중 OS·Docker 이미지·로그·H2 백업을 빼면 **사용 가능 약 20 GB [가정] 기준 약 9일 (30 GB 전부면 13일)** 이면 찬다. `model.py` 가 내는 값은 30 GB 기준인 13일이다(`tiers.json` 의 `diskBudgetGB` 30). 9일은 위 20 GB 가정으로 나눈 값이다.
- T3: 69 GB/일. VM 디스크 하나로는 하루도 버티지 못하므로 오브젝트 스토리지가 필요하다(설계 문서 `docs/SCALE.md` [계획]).
- 공개 전에 업로드·GLB 보존 정책이 필요하다(안건 #21). 부하 시험은 별도 볼륨(`beside-loadtest-storage`)에 쓰고, 중단 조건에 디스크 80 %를 둔다.

## 8. 합격 기준 [제안값 — 계약 회의 전]

RTT_base 는 A0(연기 시험)에서 잰 healthz p50 이다. 네트워크 왕복은 빼고 서버·프록시의 몫만 기준으로 삼기 위해서다.

| 엔드포인트 | p95 | p99 |
|---|---|---|
| healthz | RTT_base + 50 ms | RTT_base + 150 ms |
| `GET /jobs/{id}` | RTT_base + 100 ms | RTT_base + 300 ms |
| `POST /jobs` (0.8 MB) | 1.5 s (서버 `uploadMs` p95 ≤ 300 ms) | 3 s |
| `GET asset` (1.5 MB) | 첫 바이트 RTT_base + 150 ms, 전체 3 s | 전체 6 s |

공통 기준:
- 5xx·연결 오류 < 0.5 %. 의도한 4xx·429·503 은 따로 센다.
- 600초를 넘긴 흐름 0건, 완료 처리량 ≥ 들어온 양의 95 %. k6 가 끝까지 기다리지 못해 결과를 모르는 흐름(드레인에서 잘린 흐름)이 하나라도 있으면 통과가 아니다. 가장 느린 흐름이기 때문이다.
- 정한 도착률을 다 걸지 못한 단계(k6 `dropped_iterations` > 0)는 통과가 아니다. 단계마다 시나리오가 따로인 A2·A3·A4 는 그 단계만 실패다. 한 시나리오로 모든 단계를 거는 A1·A5·A6 은 drop 을 단계에 묶지 못하므로 어느 단계도 통과로 치지 않고 깨지는 지점도 내지 않는다.
- VM CPU 단계 평균 < 85 %, GC 뒤 힙 < 75 %. GC 뒤 힙은 마지막 GC 뒤 long-lived 풀(G1 Old Gen, 최대 = `-Xmx`)의 사용/최대, `max(jvm_memory_usage_after_gc_percent{area="heap",pool="long-lived"})`(0~1, `collect.py` 의 `jvm_heap_after_gc`)로 본다. 힙 사용/최대(`jvm_memory_used_bytes`)는 Eden 을 포함한 순간값이라 GC 사이에 톱니처럼 오르내려 판정에 쓰지 않는다.

시험별 기준:
- **A2**: 폴링하는 id 는 모두 있는 작업이므로 200 이 아닌 4xx(404 등)는 전체와 단계마다 0건이다(`load_unexpectedCount == 0`; 5xx·연결 오류는 공통 오류 기준으로, 429 `RATE_LIMITED`·503 `QUEUE_FULL` 은 `load_rejectedCount` 로 따로 센다). 빠른 404 는 오류로 세어지지 않고 지연 기준도 통과하기 때문이다. PENDING 쪽 id 는 실행 끝까지 PENDING 이어야 한다. 부하가 끝난 뒤 최대 20개를 다시 GET 해 다른 상태나 404 가 하나라도 있으면(`load_pendingLeft == 0` 실패) 그 실행의 PENDING 폴링 일부는 PENDING 작업이 아니었으므로 A2 가 아니다.
- **A3**: 업로드는 모두 유효하므로 202 가 아닌 4xx(413·400, 프록시의 404·413, `RATE_LIMITED` 코드가 없는 429)는 전체와 유지 구간마다 0건이다(`load_unexpectedCount == 0`). 빠른 거절은 지연 기준도 통과하기 때문이다. 429 `RATE_LIMITED`·503 `QUEUE_FULL`(아직 계약에 없는 코드)은 `load_rejectedCount` 로 따로 세고 기준이 없다. 이 거절이 A3 유지 구간을 실패로 만드는지는 정하지 않았다(안건 #19·#20). 위 표의 1.5·3초는 0.8 MB 업로드의 기준이라, 20 MB 업로드의 지연은 유지 구간마다 기록만 하고 판정하지 않는다.

- **깨지는 지점**: 유지 구간에서 위 기준을 처음 넘는 단계다. 아래 중단 조건의 오류 기준(k6 누적 오류 비율, 가드의 5xx 비율)이 멈춘 단계도 깨진 단계로 친다. 통과는 유지 구간을 끝까지 돌고 그 구간에 시작한 흐름이 모두 끝난 단계뿐이다. 보고하는 용량은 마지막으로 통과한 단계다(요약의 `breakingPoint.lastPassingStage`). 단계가 올라가기만 하는 시험(A1~A4)에 쓰고, 운영 상한(그 단계 사용자 수의 70 %, `operatingLimitUsers`)은 사용자 수로 단계를 거는 A1 에만 둔다. A5(스파이크·회복)와 A6(소크 한 단계)는 깨지는 지점 없이 단계별 판정만 본다.
- **중단 조건**: 오류 > 5 %가 1분 지속되거나 디스크 > 80 %이면 멈춘다. k6 가 스스로 멈춘다: 누적 오류 비율 > 5 %(첫 1분 뒤부터, `abortOnFail`, k6 종료 코드 99)와, `PROM_URL` 을 주면 가드가 보는 서버의 최근 1분 5xx 비율 > 5 %(15초 간격 2번 연속)·디스크 > 80 %(108). A0(`smoke.js`)·F3(`f3_uploads.js`)·F4(`f4_abort.py`)에는 이 둘이 없어 사람이 Ctrl+C 한다. 단계를 깨질 때까지 올리는 A1~A4 에서 오류 기준(누적 오류 비율, 가드의 5xx 비율)이 멈춘 것은 탐색의 예정된 끝이다(위 '깨지는 지점'): 부하가 멈춘 뒤 healthz 가 200 이고 5xx 비율이 0 으로 돌아오면 수집하고 다음 실행으로 간다. 부하가 멈춘 뒤에도 오류가 이어지거나 디스크 > 80 %이면, 그리고 그 밖의 시험(A0·A5·A6·G·F)은 그 자리에서 멈추고 기본 스택으로 복구한다(`deploy/loadtest/README.md` '지키는 것').

**G 시리즈의 도착과 예측** [계획]:

- **도착은 포아송이어야 한다.** M/D/1·M/M/1 은 도착 간격이 지수분포(포아송 도착)라고 놓은 식이다. k6 의 `constant-arrival-rate` 는 반복을 일정한 간격으로 시작하므로, 그대로 쓰면 도착이 D/D/1 에 가깝고 ρ < 1 에서 대기가 거의 0 이 되어 위 식과 비교할 수 없다. 그래서 `gpu_queue.js` 는 솎아내기(thinning)로 포아송 도착을 만든다. 반복을 λ·K 의 속도로 시작하고, 각 반복은 1/K 확률로만 흐름을 진행한다(K = `ARRIVAL_THIN`, 기본 20). 도착 간격은 기하분포이고 K 가 크면 지수분포에 가깝다. 쓴 방식은 요약의 `meta.arrivalProcess` 에 남는다.
- **서비스 시간은 T_SEC 보다 길다.** backend 는 추론 슬롯을 작업 하나 동안 잡는다. 슬롯 안에서 차례로 스텁의 `/healthz` 를 새로 부르고(prod 의 `inference.offline-wait-ms` > 0), Tailscale 너머로 사진을 올리고, 스텁의 지연(T_SEC)을 기다려 GLB 를 내려받아 저장하고, `job_runs`·`events.jsonl` 을 쓰고, 정리(`DELETE /artifacts/{jobId}`)를 보낸다. 그래서 위 표의 참고 값(슬롯 시간 = T_SEC)보다 실제 ρ 와 Wq 가 크다.
- **예측은 실행 뒤 잰 값으로 다시 계산한다.** `gpu_queue.js` 가 두 값과 그 값을 넣은 명령(`meta.recompute`)을 요약에 남긴다.
  - 도착률: 실제로 만든 작업 수(생성 요청 수, `load_postMs` count = `meta.measuredCreates`) × 3600 ÷ 도착 구간(`meta.measuredArrivalWindowS`: `DURATION_S`, 부하가 일찍 멈췄으면 setup 이 끝난 뒤 멈출 때까지의 초) = `meta.measuredJobsPerHour` 건/h. 솎아내기라 작업 수가 실행마다 다르므로(포아송, 표준편차 ≈ √건수) 요청한 λ 대신 이 값을 쓴다.
  - 평균 슬롯 시간: k6 가 COMPLETED 응답에서 읽은 서버 `processingMs` 의 평균(`meta.measuredProcessingMs.mean`, 서버 쪽은 `events.jsonl` 또는 Prometheus `beside_job_processing_seconds_sum / _count`). `processingMs` 는 업로드·스텁 지연·GLB 내려받기·저장뿐이라 슬롯보다 조금 짧다(작업마다 스텁 왕복 두 번 남짓과 기록). 앞의 `/healthz` 는 그 작업의 `queuedMs` 에 들어가므로 큐가 비어도 `queuedMs` 에 스텁 왕복 한 번쯤이 남는다.
  - F 실행(F1a·F1b·F2)과 retry 가 한 번이라도 있는 G 실행은 다시 계산하지 않는다(`meta.recompute` null). retry 는 도착을 늘리고 실패한 시도가 슬롯 시간에 섞이기 때문이다.

  ```
  python scripts/load/model.py --queue-rate-per-h <meta.measuredJobsPerHour> --queue-service-s <meta.measuredProcessingMs.mean / 1000> --queue-slots <c>
  # ρ, M/M/c Wq, c=1 이면 M/D/1 Wq. --json 을 붙이면 같은 값을 JSON 으로
  ```

- 서비스 시간이 조금씩 흔들리면(업로드·내려받기) 실제 큐는 M/G/1 이다. 서비스 시간의 변동계수가 0~1 이면 M/G/1 의 Wq 는 M/D/1 과 M/M/1 사이에 온다(Pollaczek–Khinchine 식). 측정한 `queuedMs`(요약의 `meta.measuredQueuedMs`, 서버 `timings.queuedMs`)를 이렇게 다시 계산한 두 값과 비교한다.

## 10. 정직성 규칙

- 루프백 결과는 버전 비교에만 쓴다. mock 결과는 "생성을 뺀 API 처리량", 스텁 결과는 "큐 동작 검증(생성 시간은 가정 T)"이라고 적는다.
- k6 VU 수는 동시 사용자 수가 아니다. 사용자 수는 도착률로 환산해 적는다.
- "API 계층이 T3를 통과했다"는 다음을 모두 만족할 때만 쓴다: T3 요청률 10분 유지, `dropped_iterations` 0, 8절 기준 충족, 클라이언트 CPU < 70 %, 업링크 비포화. 못 넘으면 "최대 지속 처리량 Y RPS(T3의 k %)"로 쓴다.
- 결과는 [실험 결과]로 적고 조건(VM 사양, 커밋 SHA, k6 버전, 업링크, 사진 크기)을 붙인다.
- [실험 결과] 후보는 `collect.py` 가 run.json 에 `resultCandidate` true 로 적은 실행뿐이다. 로컬 실행, 용량과 무관하게 멈춘 실행(setup 실패, 가드의 디스크 기준, 처음부터 `GUARD_BLIND_ABORT`(기본 3)번 연속 Prometheus 를 못 읽어 가드가 멈춘 실행, Ctrl+C·REST 정지, 드레인에서 잘린 흐름), 끝난 방식을 모르는 요약(`outcome.ended` = `unknown`)은 false 이고 `status` 가 "인용하지 않는다"로 시작한다(로컬은 "동작 확인용"). k6 오류 기준(abortOnFail)이나 가드의 5xx 기준이 멈춘 실행(`outcome.ended` = `ruleStop`)은 후보로 남지만 이 이름은 멈춘 규칙만 말한다. 그 시각에 서버 재시작·재배포·네트워크 끊김이 없었음을 VM 쪽 기록(`vm/backend.log`)과 k6 출력으로 확인한 뒤에만 `breakingPoint` 를 용량 한계로 쓴다. 가드가 멈추지 않고 Prometheus 응답 일부를 못 읽은 실행(`verdict.guard.failures` > 0)은 후보로 남되 `status` 에 "주의"가 붙는다.
- VM(Docker·Caddy·실제 Prometheus)에서 k6 로 실제로 돌리기 전에는 이 문서의 어떤 값도 측정값처럼 쓰지 않는다. 개발 PC 의 로컬 k6 실행은 동작 확인이다(9절).

## 11. 이름

- k6 쪽 값은 `load.` 접두사를 쓴다(k6 는 이름에 점을 못 써서 `load_postMs` 처럼 밑줄로 적는다). `bench.*` 처럼 `docs/perf` 전용이고 [METRICS.md](../../METRICS.md) 에 등록하지 않는다(안건 [#15](../../api/REVIEW_CHECKLIST.md)).
- 서버 운영 지표 `beside.*`(Micrometer, Prometheus 이름은 `beside_jobs_finished_total` 등)는 METRICS 에 추가로 적는다(같은 브랜치의 Java 조각). 8절 기준에 쓰는 Spring 내장 지표(`process_cpu_usage`, `system_cpu_usage`, `jvm_memory_usage_after_gc_percent`)는 METRICS §5.2 의 이름 그대로다.
- 서버 값 `uploadMs`·`queuedMs`·`processingMs`·`totalMs` 는 METRICS §1 의 뜻 그대로 쓴다.

## 12. 데이터 위치와 다시 계산

- 원시 결과: k6 실행마다 한 폴더 `docs/perf/load/data/<YYYY-MM-DD_HHMM>-<RUN_ID>/` 에 그 실행의 k6 summary, `collect.py` 가 쓰는 `run.json`·Prometheus 구간 CSV 18개(8절 'GC 뒤 힙' 의 `jvm_heap_after_gc` 포함), 그 실행의 VM 쪽 파일(`vm/`, run.json 에는 `collect.py --attach` 로만 들어감)이 모인다. 절차는 `deploy/loadtest/README.md` 5번. k6 스크립트와 수집 도구는 [scripts/load/](../../../scripts/load/).
