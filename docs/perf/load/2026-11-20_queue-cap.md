# 큐 상한(안건 #21) 회의 자료 — 상한 N 과 Retry-After

작성 2026-11-20. 계약 회의가 안건 #21([REVIEW_CHECKLIST.md](../../api/REVIEW_CHECKLIST.md) 27행)을 정할 때 보는 자료다. #21 의 결정 칸은 회의가 채운다. 이 자료로 #21 행을 고치지 않는다.

표기:
- **[실험 결과]** 부하 시험 데이터 폴더에 원시 값이 있는 측정. 이 자료를 위해 새로 잰 것은 없다.
- **[계산]** 측정값으로 계산한 값. 숫자 옆에 다른 출처(식이나 문서)를 적지 않았으면 [scripts/load/cap_model.py](../../../scripts/load/cap_model.py) 의 출력 [data/2026-11-20_queue-cap/cap_model-output.txt](data/2026-11-20_queue-cap/cap_model-output.txt) 에 있다. "출력 n절" 은 그 파일의 `== n.` 이다.
- **[가정]** [scripts/load/tiers.json](../../../scripts/load/tiers.json) 의 가정.
- **[제안값]** 회의가 고를 값.
- **[계획]** 아직 하지 않음. **큐 상한 자체가 main 기준 [계획] 이다.** 서버·웹·Unity 코드와 시험은 회의 전 검토 브랜치 `review/queue-cap-2` 에만 있다(main 미병합).

## 1. 목적

- 대기열에 상한이 없어 넘치는 요청이 끝없이 쌓인다.
- 대기 작업이 N 건 이상이면 생성·retry 를 503 `QUEUE_FULL` + `Retry-After` 로 바로 거절하려고 한다. 받아들인 작업의 최악 대기를 정해 두려는 것이다.
- 처리량은 늘지 않는다(6절).
- 회의가 정할 것은 D1~D11 이다(9절). 이 자료는 그 판단에 쓸 숫자를 낸다.

## 2. 지금 상태

- 상한이 없다. PENDING 이 끝없이 쌓인다.
- GPU 1대·슬롯 1개는 시간당 약 415건을 처리한다(4차 `g3c1`, S_busy 8.67 s) [실험 결과·계산, [2026-11-20_vm-4th.md](2026-11-20_vm-4th.md) 요약]. 2차 Pod 는 409건/h(8.81 s)였다 [실험 결과·계산, [2026-11-18_vm-2nd.md](2026-11-18_vm-2nd.md) 4절].
- 과부하 시험의 대기 최대는 205 s(4차 `queuedMs`)·228 s(2차 슬롯 대기)였다 [실험 결과, 같은 두 문서]. 생성 → COMPLETED 로 재면 213 s·238 s 다 [계산, 출력 3·4절].
- 앱은 폴링을 600 s 에 포기한다(`unity/Assets/Beside/Job/JobManager.cs:27` `maxWaitSeconds`).
- GPU 가 꺼져도 작업은 PENDING 으로 최대 30분 기다린다(`backend/src/main/resources/application-prod.properties:27` `inference.offline-wait-ms=1800000`).

## 3. 상한 규칙

**대기**는 작업 생성(INSERT) → COMPLETED 다. 앱의 600 s 가 세는 구간이다.

대기 작업이 N 건 이상이면 거절한다. 그러면 받아들인 작업 앞에는 많아야 N−1건과 슬롯의 1건이 있다. 예외 두 가지(오래된 PENDING 은 세지 않음, 같은 키의 겹친 요청은 함께 접수)는 9절 D12 다. 예외 두 가지(오래된 PENDING 은 세지 않음, 같은 키의 겹친 요청은 함께 접수)는 9절 D12 다.
- **c=1**: N = ⌊W/S⌋ − 1, 최악 대기 (N+1)·S. W 는 목표 최악 대기다.
- **슬롯이 여럿**: 잰 처리량 μ(건/h)로 N = ⌊μ·(W − T)/3600⌋, 최악 대기 N × 3600/μ + T. T 는 작업 하나의 처리 시간이다. c=1 은 μ = 3600/S, T = S 인 경우다.
- **Retry-After**: R = N × 3600/μ(N건을 비우는 시간). 거절은 대기가 N건일 때만 나므로 고정값이면 된다.

### 3.1 c=1 — S_busy 8.67 s, μ 415건/h [계산, 출력 1절]

| 목표 최악 대기 W | N | 최악 대기 (N+1)·S | 600 s 까지 남는 시간 | R | S 가 11.5 s 로 늘면 최악 대기 |
|---|---|---|---|---|---|
| 120 s | 12 | 113 s | 487 s | 104 s | 150 s |
| **180 s [제안값]** | **19** | **173 s** | **427 s** | **165 s** | **230 s** |
| 300 s | 33 | 295 s | 305 s | 286 s | 391 s |
| 600 s (기존 공식) | 68 | 598 s | 2 s | 590 s | **793.5 s — 600 s 를 넘음** |

- 11.5 s 는 2차 Pod 의 S0 다 [실험 결과·계산, vm-2nd 2절]. S 는 Pod·경로마다 바뀐다.
- "600 s 까지 남는 시간"은 받아들인 작업이 GPU 끊김을 견딜 수 있는 시간이다. 3차에는 계획 밖 끊김이 약 83 s·49.6 s 있었다 [실험 결과, [2026-11-19_vm-3rd.md](2026-11-19_vm-3rd.md) 요약].

### 3.2 기존 값을 추천하지 않는 이유

- **Q_max = 9**(#21 과 [TRAFFIC_MODEL.md](TRAFFIC_MODEL.md) §4 의 값)는 생성 시간 T = 60 s 가정이다. 잰 S(8.67 s)로는 최악 대기가 87 s 라 필요보다 많이 거절한다 [계산, (9+1) × 8.67].
- **600 s 공식(N = 68)** 은 여유가 없다.
  - 최악 대기 598 s 로 앱의 600 s 와 2 s 차이다. S 가 11.5 s 로 늘면 793.5 s 다 [계산, 출력 1절].
  - 계속 넘치면 받아들인 작업 거의 모두가 10분 가까이 기다린다. 평균 559~577 s, 최대 601~602 s 다 [계산, 출력 5절 정상 상태].
  - 20분 실행으로는 차지 않는다. 471건/h 도착이면 차는 데 약 73분이 걸린다 [계산, 출력 2절]. 그래서 시험으로 확인하기도 어렵다.

### 3.3 c=2 — μ₂ 495건/h(센 하한), T₂ 9.86 s [계산, 출력 1절]

| W | N | 최악 대기 | R |
|---|---|---|---|
| 120 s | 15 | 119 s | 109 s |
| **180 s** | **23** | **177 s** | **167 s** |
| 300 s | 39 | 294 s | 284 s |

- 같은 A40 의 슬롯 2개는 처리량이 2배가 아니다(1.19배 이상) [실험 결과·계산, vm-4th 요약]. 그래서 c=1 값을 두 배로 하거나 공식에 c=2 를 넣으면 안 된다.
  - 2 × 12 = 24 → 최악 184 s(목표 120 s).
  - 600 s 공식에 c=2 를 넣으면 N = 112 → 최악 824 s(처리량이 하한일 때).
- **슬롯 수나 GPU 수를 바꾸면 N 과 R 을 함께 다시 계산한다.**

## 4. 실제 도착으로 다시 돌린 결과 [계산, 출력 3·4절]

과부하 시험의 실제 도착·크롭·처리 시간을 상한 N 의 문으로 다시 돌렸다.
- 슬롯은 처리 + 넘김(앞 작업 처리 끝 → 기다린 다음 작업 처리 시작의 중앙값)을 잡는다. 슬롯은 요청 순서대로 준다.
- `run.json` 의 실행 구간 안에서 생성된 작업만 쓴다. `events.jsonl` 에는 앞 실행의 줄도 있다(g3c1 은 189줄 중 157건).
- **재현 확인**: 상한 없이 돌리면 평균 대기가 g3c1 은 측정과 −0.2 %, g3r165 는 +5.6 % 다. 2차 문서의 FIFO 재현(평균 3~6 % 안, 재현이 조금 높음)과 같은 수준이다.

| 실행 | 상한 | 거절 | 받아들인 작업 최대 대기 | (N+1)·S_busy |
|---|---|---|---|---|
| 4차 `g3c1`(잰 471건/h) | 없음 | 0 / 157 | 재현 213 s(측정 213 s) | — |
| | N 12 | 12 / 157 (7.6 %) | 112.6 s | 112.7 s |
| | **N 19** | **5 / 157 (3.2 %)** | **174.1 s** | 173.4 s |
| 2차 `g3r165`(잰 483건/h) | 없음 | 0 / 161 | 재현 250 s(측정 238 s) | — |
| | N 12 | 16 / 161 (9.9 %) | 115.4 s | 114.6 s |
| | **N 19** | **9 / 161 (5.6 %)** | **175.5 s** | 176.2 s |

- 최대 대기가 (N+1)·S_busy 를 1 s 안에서 넘을 수 있다. S_busy 는 평균이고, 작업마다 처리 시간이 다르기 때문이다.
- 이 두 실행에서 도착이 본 대기 작업은 최대 23건·26건이었다 [계산, 출력 3·4절]. 재생으로는 N 24 이상(g3c1)·28 이상(g3r165)이면 아무것도 거절하지 않는다. 그래서 지난 20분 실행들로는 이보다 큰 상한을 확인할 수 없다.

## 6. 상한이 하지 않는 것

- **처리량을 늘리지 않는다.** 정상 상태에서 받아들인 작업은 상한과 상관없이 시간당 413~416건으로 GPU 용량과 같다 [계산, 출력 5절]. 처리량은 슬롯·GPU 를 늘리거나 작업당 시간을 줄여야 는다.
- **업로드 대역을 줄이지 않는다.** 거절은 본문을 다 받은 뒤(사진 검사 전) 서비스 안에서 한다. 아끼는 것은 사진 검사·저장·INSERT 다. 대역은 앱이 `Retry-After` 를 지킬 때만 준다. 이것은 설계에서 나온 것이고 재지 않았다 [계획].
- **한 클라이언트가 대기열을 채우는 것은 막지 않는다.** 그것은 #22(요청 제한, 429) 몫이다.
- **GPU 꺼짐을 따로 알리지 않는다.** 꺼져 있을 때도 같은 `QUEUE_FULL` 이다. 그래서 D8 문구가 두 경우에 다 맞아야 한다.

## 7. Retry-After 와 재시도 흐름

- **규칙**: R = N × 3600/μ. c=1·N 19 면 165 s, c=2·N 23 이면 167 s 다 [계산, 출력 1절].
- 거절된 사용자가 R 초 뒤 같은 사진을 다시 올린다고 보고 흉내 냈다 [계산, 출력 6절]. 조건은 517건/h, N 19, 20시간, 거절된 업로드 0.8 MB [가정].

| 사용자 행동 | R | POST /h (사용자당) | 거절된 POST /h | 거절된 업로드 |
|---|---|---|---|---|
| 최대 5번까지 | 10 s | 1,380 (2.69) | 964 | 771 MB/h |
| | 60 s | 1,342 (2.61) | 926 | 741 MB/h |
| | 165 s | 1,314 (2.56) | 899 | 719 MB/h |
| 첫 POST 뒤 600 s 동안 계속 | 10 s | 14,497 (28.22) | 14,081 | 11,265 MB/h |
| | 60 s | 3,029 (5.90) | 2,613 | 2,091 MB/h |
| | **165 s** | **1,111 (2.16)** | **696** | **557 MB/h** |

- 횟수로 제한하는 사용자에게는 R 이 거의 상관없다. 시간으로 버티는 사용자(앱이 R 뒤 다시 시도를 열어 주면 이쪽에 가깝다)에게는 짧은 R 이 POST 를 크게 늘린다.
- 받아들이는 수(시간당 416건)와 결국 포기하는 사용자(약 19 %)는 R 과 상관없다 [계산, 출력 6절].
- 도착은 20시간 뒤에도 첫 POST → 마지막 재시도의 가장 긴 시간만큼 더 흘린다. 그래야 마지막 사용자들의 재시도가 비어 가는 대기열이 아니라 같은 부하를 만난다.
- 앱은 자동으로 다시 보내지 않는다. 이 초안 브랜치의 웹 Mock UI 와 Unity 는 `Retry-After` 동안 생성(새 사진 포함)·다시 시도 버튼을 잠그고, 시간이 지나면 사용자가 다시 눌러야 보낸다([ERROR_CODES.md](../../api/ERROR_CODES.md) '대기열 상한'). 둘 다 서버와 같은 검토 브랜치에만 있다(main 미병합). 웹은 node 시험을 통과했고, Unity 는 컴파일만 확인했으며 에디터·기기 확인은 [계획] 이다. main 의 Unity 는 `Retry-After` 를 읽지 않는다.

## 8. GPU 꺼짐 [계산, 출력 1절]

- prod 는 추론 서비스가 내려가면 작업을 PENDING 으로 최대 30분 둔다(2절). 공개 베타 피크 120건/h [가정] 로 30분 꺼지면:
  - 상한이 없으면 60건이 쌓이고, GPU 가 돌아온 뒤 비우는 데 520 s 가 걸린다.
  - N 19 면 대기는 19건으로 묶이고 비우는 데 165 s 다. 꺼진 동안 온 60건 중 41건은 거절된다.
- 받아들인 작업은 3.1절의 "600 s 까지 남는 시간"(N 19 면 427 s)보다 길게 꺼지면 앱의 600 s 에 걸린다.
- 꺼졌을 때 다른 `Retry-After` 를 보내는 것은 [계획] 이고 MVP 밖이다.
- 상한은 폴링 부하도 묶는다. 시스템 안 작업이 c + N 건 이하라 2초 폴링은 (c + N)/2 RPS 이하다. N 19 면 10 RPS 다 [계산, TRAFFIC_MODEL.md §6 의 식].

- 실제 도착 재생에서 거절은 3.2 %(4차)·5.6 %(2차)였다(4절).
- R 165 s 는 시간으로 버티는 사용자의 POST 를 R 10 s 의 1/13 로 줄인다(7절 표의 1,111 ÷ 14,497).

## 10. 5차 부하 시험에서 확인할 것 [계획]

실제 A40, 같은 Pod 에서 상한 0 실행과 상한 N 실행을 비교한다. 합격 기준:
1. 거절은 모두 503 + `QUEUE_FULL` + `Retry-After`=R 이다(k6 check). 다른 5xx 는 0 이다(503 수 = `load_rejectedCount`).
2. DB PENDING 이 N 을 넘지 않는다(`beside_jobs_queue{state="pending"}` 최대). 거절 로그마다 pending+reserved ≥ N 이다. 예외: `beside_jobs_pending_stale` 이 0 보다 큰 동안과 v0(상한 없음, Caddy 가 막음)의 작업, 같은 키의 겹친 요청(D12). 예외: `beside_jobs_pending_stale` 이 0 보다 큰 동안과 v0(상한 없음, Caddy 가 막음)의 작업, 같은 키의 겹친 요청(D12).
3. 받아들인 작업의 최대 대기 ≤ (N+1)·S_busy + 10 s 다. N=19 면 약 184 s 다(상한이 없을 때 205~228 s).
4. k6 거절 수 = 서버 카운터 증가다(시작·끝 순간값, op 별).
5. 포화 구간의 처리량이 상한 0 실행과 ±5 % 안이다. 상한이 GPU 처리량을 깎으면 안 된다.
6. 실행 길이는 실제 도착률로 정한다. 4차는 요청 517건/h 에 실제 471건/h, 용량 415건/h 였다. 순증 약 56건/h 라 N=19 가 차는 데 약 20분이 걸린다. 그래서 40분 돌린다.

참고 [계산]:
- 6번의 20분은 유체 근사다(출력 2절). 몬테카를로로는 471건/h 에서 첫 거절이 중앙값 873 s(5~95 %: 346~2,015 s)에 오고, 40분 실행의 97.8 % 에서 거절이 난다(출력 5절).
- 3번의 +10 s 여유는 재생에서 본 초과(1 s 안)와 정상 상태 최대 175.6 s 를 덮는다(출력 3·5절).
- 거절 비율은 그 실행의 실제 도착률로 `cap_model.py montecarlo` 를 다시 돌려 5~95 % 구간과 견준다. 그 실행의 도착을 `replay` 로 다시 돌린 결과도 함께 적는다.
