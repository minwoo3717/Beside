### S_busy 와 N·`Retry-After`

- S_busy 는 8.67 → 8.81 s(+0.14 s)로 늘었다 [실험 결과·계산]. 처리 시간이 늘어난 곳은 GLB 구간(Pod 가 GLB 를 넘긴 뒤 → VM 저장 끝)뿐이다. 중앙값이 1.75 → 1.99 s 였다 [계산]. GLB 가 털 맵만큼 45 % 커진 것 때문으로 본다 [가설: Pod·날이 4차와 다르다].
- 같은 규칙으로 **N 은 19 그대로**다. **`Retry-After` 는 167 s** 가 나왔다. 결정값 165 s 와 2 s 다르다 [계산]. 이 값은 [실험 결과]로만 적었다. 결정 기록(#21)·CHANGELOG `api-v1.1`·compose 기본값(165)은 바꾸지 않았다. 바꿀지는 사용자가 정한다 [계획].

### 상한 0 대 상한 19

- 상한 19 실행은 회의 자료 10절의 기준 1~5 를 모두 통과했고, 6(실행 길이)의 조건도 채웠다 [실험 결과·계산] (5절).
- 사용자가 본 것 [실험 결과·계산] (6절):
  - 상한 0: 만든 383건 가운데 132건(34.5 %)이 k6 의 600 s 흐름 시간 초과로 끝났다. 그중 100건은 사용자가 떠난 뒤 서버가 끝까지 처리했다.
  - 상한 19: 337건 가운데 51건(15.1 %)이 바로 503 + `Retry-After` 167 s 를 받았다. 받아들인 286건은 모두 182.9 s 안에 흐름을 마쳤다.
  - 두 실행의 실제 도착률은 달랐다(575 대 505.5건/h, 같은 요청 λ 517건/h 의 포아송 흔들림). 같은 도착으로 견준 값은 상한 0 실행의 재생이다. N 19 를 걸면 345건 중 79건(22.9 %)을 거절하고, 받아들인 작업의 최대 대기는 176.3 s 다 [계산].
- 상한은 GPU 처리량을 깎지 않았다. 두 실행의 S_busy 비가 0.9999 였다 [계산].

## 4. N·`Retry-After` 다시 계산 [계산]

회의 자료 3절의 규칙(c=1, 목표 최악 대기 W=180 s)을 그대로 썼다(`cap_model-formula.txt`, 출력 `== 4.`):
- N = ⌊180 / S_busy⌋ − 1.
- 최악 대기 = (N+1)·S_busy.
- `Retry-After` R = N·S_busy 를 정수 초로 반올림.

| 값 | 4차 `g3c1` (결정의 근거) | 5차 `g3cap0` |
|---|---|---|
| S_busy → μ | 8.67 s → 415건/h | 8.81 s → 409건/h |
| N | 19 | **19** (결정과 같음) |
| 최악 대기 (N+1)·S | 173.4 s | 176.2 s (앱의 600 s 까지 423.8 s 남음) |
| R = N·S | 164.7 → **165** | 167.4 → **167** (결정과 다름) |

- N 19 는 S_busy ≤ 9.00 s 이면 그대로다. 5차 값은 그 경계까지 0.19 s 남는다.
- R 165 는 S_busy 가 8.658~8.711 s, R 167 은 8.763~8.816 s 일 때 나온다. 다른 Pod 의 2차 `g3r165`(8.81 s)도 167 이었다. 그래서 R 은 Pod·날·GLB 크기에 따라 165~167 사이에서 움직인다.
- R 은 거절된 요청이 다시 올 때까지의 시간이다. 받아들인 작업의 대기(기준 3)에는 들어가지 않는다. 165 를 그대로 두면 거절된 사용자가 약 2 s(1.2 %) 일찍 다시 온다.
- **처리**: 런북대로 상한 N 실행은 다시 잰 값(N 19, R 167)으로 했다. 결정 기록(`docs/api/REVIEW_CHECKLIST.md` #21)·CHANGELOG `api-v1.1`(N 19·165 s)·compose 기본값 `ADMISSION_RETRY_AFTER_SECONDS:-165` 와 `LOADTEST_ADMISSION_RETRY_AFTER_SECONDS:-165` 는 바꾸지 않았다. 회의 자료 10절은 "달라지면 #21 의 값을 고친다" 고 적었지만, 이번 밤 승인은 [실험 결과]로만 적고 사용자에게 묻는 것이었다 [계획].
- 몬테카를로·차는 시간(상한 0 실행의 표본, `cap_model-mc.txt`·`cap_model-fill.txt`):
  - 575건/h·N 19·40분: 거절 24.6 %(5~95 %: 17.8~30.7 %), 첫 거절 중앙값 367 s(181~711 s).
  - 빈 큐에서 N 19 가 차는 시간(유체 근사): 6.9분.
