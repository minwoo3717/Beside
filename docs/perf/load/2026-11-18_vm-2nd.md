- **슬롯 1개(c=1)·이 경로(서울 VM ↔ 스웨덴 Pod)·이 사진에서, A40 한 대 앞의 처리 용량은 시간당 약 400건이다** [계산: 3,600 ÷ S_busy].
  - 과부하 두 실행에서 슬롯이 쉬지 않을 때 작업 시작 간격(S_busy)이 8.81~9.06 s 였다(397~409건/h) [실험 결과].
  - G1r 에서 이어서 처리할 때의 간격은 9.9~10.7 s 로 더 길었다.
  - 이것은 GPU 자체의 한계가 아니다(사용률 22.7 %, 아래). 슬롯 2개(G2r)는 이 차례에 못 했고 3차에서 했다([2026-11-19_vm-3rd.md](2026-11-19_vm-3rd.md) 4절).
- **backend 의 GPU 슬롯은 FIFO 단일 슬롯대로 동작한다** [계산].
  - 실제 도착 시각과 처리 시간을 넣어 FIFO 대기를 다시 계산했다(린들리 점화식). 4개 실행 모두 측정 대기와 평균 3~6 % 안에서 맞았다(재현이 조금 높음, 3절).
  - 슬롯 사이 넘김(앞 작업의 `DELETE` + 다음 작업의 `/healthz`)은 중앙값 0.83 s 다.
- **실행 전 예측과 측정이 달랐다**. 예측은 S0 = 11.5 s·요청 λ 로 놓은 M/D/1 이었고(5.8 s·13.4 s), 측정은 3.4 s·8.1 s 였다 [계산, 3절].
  - 슬롯은 S0 보다 짧았지만(10.0~10.7 s) 실제 도착이 요청보다 10·14 % 많았다. 그래서 실제 ρ 는 0.48·0.74 로 계획과 거의 같았다.
  - 잰 λ·잰 슬롯의 정상 상태 대기(P-K)는 4.8 s·16.8 s 다.
  - ρ0.5 의 측정은 25분 실행의 흔들림 안이다(몬테카를로 27번째 백분위).
  - ρ0.7 의 측정은 그보다 낮다(작업 수를 고정한 몬테카를로 3번째 백분위). 느린 14건이 두 묶음으로 몰려 온 순서 때문이다. 같은 슬롯 값을 무작위 순서로 넣으면 평균 대기는 10.6 s 다.
- **포화 상태에서도 GPU 는 대부분 쉬었다**.
  - 과부하 재실행 동안 GPU 사용률 평균은 22.7 %(nvidia-smi 5초 표본)였다 [실험 결과].
  - 슬롯 8.9 s 중 모델(추론+변환)은 4.5 s 이고, 나머지는 전송 등(약 3.5 s)과 넘김이다.
  - 추론 구간 안에서도 사용률은 평균 46~51 % 였다 [계산]. 그래서 전송을 슬롯 밖으로 빼도 사용률은 약 50 % 를 넘기 어렵다.
- **부하가 있을수록 전송이 빨랐다** [실험 결과]. 전송(처리 − 추론 − 변환) 평균이 G0r 5.43 s 에서 과부하 재실행 3.53 s 로 줄었다.
  - Pod 접근 로그의 클라이언트 포트로 세면, G0r 의 31건은 모두 새 연결이었고 과부하 재실행의 161건은 연결 2개로 갔다.
  - 같은 실행 안에서도 이어 쓴 연결의 전송이 새 연결보다 평균 0.5~1.3 s 짧았다 [계산].
  - 원인은 새 연결의 연결 맺기·슬로 스타트로 본다 [가설]. Pod 의 uvicorn 은 기본값대로 5초 쉬면 연결을 닫는다.
- **GPU 대수** [계산]: 잰 슬롯(8.8~11.5 s)으로 다시 계산하면 T2(120건/h)는 1대, T3(3,600건/h)는 13~17대다. 1차 문서의 exp-01 기준은 15~23대였다.
- **VM CPU** [계산]: 작업 하나에 VM 전체 CPU 가 3.6~4.5 코어·초 들었다(backend JVM 만 3.2~3.7). 그래서 2 vCPU VM 의 CPU 70 % 를 지키는 상한은 약 1,300~1,400건/h 이고, T3 의 초당 1건에는 모자란다. 대부분이 사진 크롭이라는 것은 [가설]이다.
- **남은 작업 폴더**: 539건 중 1건의 정리 `DELETE` 가 "HTTP/1.1 header parser received no bytes" 로 실패했다. Pod 로그에도 그 `DELETE` 가 없다 [실험 결과]. backend 는 다시 시도하지 않고 Pod 에는 다른 정리가 없어, 작업 폴더(15:29 UTC 에 25 MB 확인, 원본 출력은 리포 밖)가 남았다.
- **못 한 것**: G2r(슬롯 2개)·F1b-real·F2-real·F1a. 3차에서 했다([2026-11-19_vm-3rd.md](2026-11-19_vm-3rd.md)).
  - 11:44 UTC 에 계획 검토로 진행을 멈췄다. 돌던 과부하 재실행은 11:57 UTC 에 끝났다.
  - 15:28 UTC 에 이어 갔을 때(멈춘 시간 약 3시간 31분) A40 6시간 상한(15:44 UTC)까지 16분만 남았다.
  - 그래서 상한을 지켜 A40 을 정지하고 운영을 되돌렸다.
- **운영 보호**(운영자 확인, 원본 출력은 리포 밖 VM·개발 PC):
  - 운영 backend 는 09:48~15:31 UTC(5시간 43분) 내려가 있었고, 그중 약 3시간 31분은 시험이 멈춘 시간이다.

## 2. G0r — 대기열 없는 슬롯 시간 [실험 결과·계산]

`smoke.js` 로 30초마다 흐름 1개를 15분 동안 돌렸다(VU 1개). 작업 31건이 모두 COMPLETED 였고, k6 기준도 모두 통과했다(종료 코드 0). 흐름 사이에 대기열이 생기지 않았다(동시에 있던 작업 최대 1건).

| 서버 값 (31건) | 평균 | 중앙값 | p95 | 최소~최대 |
|---|---|---|---|---|
| `processingMs` | 10,403 | 9,894 | 14,360 | 8,568~18,876 |
| `inferMs` | 4,071 | 4,008 | 4,538 | 3,699~4,670 |
| `convertMs` | 905 | 884 | 1,112 | 704~1,150 |
| 전송 등 = `processingMs` − `inferMs` − `convertMs` | 5,427 | 4,727 | 9,408 | 4,125~14,058 |
| `queuedMs` | 2,487 | 2,519 | 2,677 | 2,179~2,696 |
| `preprocessMs`(크롭, 슬롯 밖) | 1,993 | 1,992 | 2,105 | 1,878~2,137 |
| `checkMs`(사진 검사, `POST` 안) | 381 | 379 | 424 | 343~484 |
| h = `queuedMs` − `preprocessMs`(슬롯 안 `/healthz`) | 493 | **557** | 649 | 285~736 |

- ms 단위다. 모든 작업의 출력이 같았다: GLB 1,326,748 B, 정점 4,310, 삼각형 7,774, `gpuPeakMB` 5,120.
- **"전송 등"** 은 나눠 재지 않은 나머지다. 업로드·내려받기 외에 Pod 의 요청 처리와 볼륨 읽기·쓰기, VM 의 GLB 저장이 들어 있다.
- **S0 = 평균 `processingMs` + 2·h0 = 10.40 + 2 × 0.557 = 11.51 s → 11.5 s** [계산](0.5 s 단위). h0 는 h 의 중앙값이다. 이후 G1r·G3r 의 `T_SEC` 로 썼다.
- **h 는 두 무리다**.
  - 22건은 0.55~0.74 s 로, VM 에서 새 연결로 잰 `/healthz`(왕복 두 번)와 같다.
  - 9건은 0.29~0.31 s 다. 15초 주기 상태 점검이 막 연 연결을 다시 쓴 것으로 본다 [가설].
  - 슬롯 안 `/healthz` 는 업로드·내려받기와 다른 HttpClient(`InferenceHealthMonitor`)로 간다. 그래서 h 는 업로드 연결의 상태를 보여 주지 않는다(7절은 Pod 접근 로그로 본다).
- **작업 하나 나누기**: VM 로그(`stage=PROCESSING`, 저장 끝)와 Pod 로그(추론·변환 끝, `POST` 응답)로 나눴다(초).
  - Pod 로그 시각이 0~1 s 늦게 찍혀, 업로드는 아래 값보다 최대 약 1 s 작을 수 있고 'Pod 응답 → 저장 끝'은 그만큼 클 수 있다.
  - 두 기계의 시계도 맞춰 보지 않았다(NTP 가정). 네 칸의 합은 `processingMs` 와 같다.
  - 31건 전체의 업로드 상한은 1.94~2.81 s(중앙값 2.50 s)다 [계산].

| 작업 | 업로드 상한 (`PROCESSING` → Pod 추론 시작) | 추론 | 변환 | Pod 응답 → GLB 저장 끝 (하한) | `processingMs` |
|---|---|---|---|---|---|
| `3a493649` | 2.56 | 4.48 | 1.10 | 2.15 | 10.31 |
| `14adebc4` | 1.97 | 3.79 | 0.88 | 4.05 | 10.71 |
| `4be804a7` | 2.24 | 4.56 | 0.88 | 4.07 | 11.75 |

- **사용자 쪽**(k6, 왕복 145 ms 의 미국 서부):
  - `POST` 응답 뒤 폴링으로 COMPLETED 를 본 시간(`load_waitMs`)은 중앙값 13.0 s·p95 17.3 s 였다. 2초 폴링 간격이 들어 있고, `POST` 자체(중앙값 0.61 s)는 빠진다.
  - 흐름 전체(`load_flowMs`, GLB 내려받기 포함)는 중앙값 14.8 s 였다.
- **exp-01 과 비교**: 전송 등은 G0r 평균 5.43 s(중앙값 4.73 s)로 exp-01(11-17, DERP 중계) 2건의 5.47·6.80 s 보다 크게 줄지 않았다. 표본이 2건이라 차이는 가리지 못한다. 직접 연결이지만 왕복(268 ms)이 DERP(약 300 ms)와 비슷하기 때문으로 본다 [가설].

계산 방법:
- **측정 대기**: Wq = `queuedMs` − `preprocessMs` − h0(0.557 s)다. 기다리지 않은 작업은 그 작업의 `/healthz` 가 h0 와 달라 Wq 가 0 근처에서 ± 몇백 ms 흔들린다.
- **FIFO 재현** [계산, `g_trace.py`]: 슬롯 요청 시각(생성 + `preprocessMs`)과 슬롯 시간(그 작업의 `processingMs` + 넘김 중앙값)으로 W(n) = max(0, D(n−1) − 요청(n))을 계산했다.
- **몬테카를로** [계산, `g_sim.py`, 씨앗 1]: 빈 슬롯에서 시작해 포아송 도착으로 실행 시간만큼 2,000번 흉내 냈다. 슬롯 시간은 그 실행의 슬롯 값에서 다시 뽑았다.
- **새로 덧붙인 값** [계산, `g_recheck.py`]: 작업 수를 고정한 몬테카를로, 느린 작업을 뺀 P-K, 무작위 순서 재현.

읽은 것:
- **backend 슬롯은 FIFO 단일 슬롯대로 동작한다.**
  - FIFO 재현이 측정과 평균 3~4 % 안에서 맞는다. 슬롯을 놓친 작업이나 순서 뒤바뀜 같은 숨은 지연은 보이지 않는다.
  - 재현이 조금 높은 것은 주로 넘김을 모든 작업에 중앙값으로 넣었기 때문이다 [계산]. 넘김 평균(0.79·0.76 s)으로 다시 재현하면 3.43·8.16 s 로 측정과의 차가 1.8 %·0.9 % 로 준다.
- **예측과 측정의 차이** [계산]:
  1. 슬롯은 S0 보다 짧았다(10.0~10.7 s, 7절). 하지만 만든 작업이 요청보다 10·14 % 많아 실제 ρ 는 0.48·0.74 로 계획(0.5·0.7)과 거의 같았다.
  2. **ρ0.5**: 측정 3.37 s 는 몬테카를로 27번째 백분위로, 한 번의 25분 실행이 흔들리는 폭 안이다. 빈 큐 시작의 치우침 자체는 작다(몬테카를로 평균 4.64·15.61 s 대 P-K 4.76·16.84 s).
  3. **ρ0.7**: 측정 8.09 s 는 몬테카를로(포아송 개수)의 10번째 백분위다. 작업 수를 실제 125건으로 고정하면 3번째 백분위(5~95 %: 8.57~24.31 s)로 구간 밖이다.
     - P-K·몬테카를로는 느린 14건(6절)을 실행 전체에 독립으로 흩어 놓는다. 14건을 빼면 P-K 는 9.78 s 다(평균 슬롯 9.61 s, ρ 0.67).
     - 실제로는 14건이 두 묶음으로 와서 평균 대기를 1.3 s 만 늘렸다. 재현 8.43 s 가 14건을 보통 슬롯(9.61 s)으로 바꾸면 7.09 s 가 된다.
     - 같은 슬롯 값을 실제 도착에 무작위 순서로 넣으면 평균 10.6 s 이고, 실제 순서는 1번째 백분위다.
     - 그래서 ρ0.7 의 낮은 대기는 실행 길이보다 느린 작업이 몰려 온 순서 몫이다.
- **느린 작업 14건**을 빼면 ρ0.7 의 평균 `processingMs` 는 8.77 s 다(111건).

## 4. G3r — 과부하 [실험 결과·계산]

## 7. 연결 재사용과 슬롯 시간 [실험 결과·계산·가설]

연결은 Pod 접근 로그(`gpu/inference-ts.log`)의 클라이언트 포트로 셌다. tailscaled(userspace)는 들어온 연결마다 127.0.0.1 연결을 하나 연다(`deploy/runpod/start_pod.sh` 머리 주석). 그래서 포트가 같으면 같은 연결로 본다. 작업마다 GLB `GET` 의 포트를 쓰고, 그 실행에서 처음 보인 포트면 새 연결로 셌다 [계산, `g_recheck.py`].

| 실행 | 실제 ρ | 평균 `processingMs` | 전송 등 평균 / p95 | 새 연결 / 이어 쓴 연결 (작업 수) | 전송 등 평균: 새 / 이어 씀 | `inferMs` 평균 | 평균 슬롯 |
|---|---|---|---|---|---|---|---|
| G0r | 작업 사이 약 19 s 쉼 | 10.40 s | 5.43 / 9.41 s | 31 / 0 | 5.43 s / — | 4.07 s | S0 11.5 s (처리 + 2·h0), 같은 정의로는 약 11.2 s |
| G1r ρ0.5 | 0.48 | 9.19 s | 4.32 / 6.76 s | 35 / 37 | 4.82 / 3.85 s | 4.03 s | 10.02 s |
| G1r ρ0.7 | 0.74 | 9.83 s (느린 14건을 빼면 8.77 s) | 4.02 / 5.15 s | 31 / 94 | 4.99 / 3.69 s | 4.62 s | 10.67 s |
| G3r 1.3 | 0.91 | 8.31 s | 3.82 / 4.44 s | 12 / 138 | 4.27 / 3.78 s | 3.70 s | 9.14 s |
| G3r 재실행 | 1.19 | 8.06 s | 3.53 / 3.65 s | 2 / 159 | 4.68 / 3.51 s | 3.73 s | 8.89 s |

- **부하가 클수록 전송이 짧고 고르게 됐다**: 평균이 5.43 s 에서 3.53 s 로, p95 가 9.41 s 에서 3.65 s 로 줄었다 [실험 결과].
- **연결 재사용** [실험 결과]: 30초 간격의 G0r 는 작업마다 새 연결이었고, 바쁠수록 앞 작업의 연결을 이어 썼다. Pod 의 uvicorn 은 `--timeout-keep-alive` 기본값(5초)으로 뜬다(`scripts/start_inference_wsl.sh` 에 설정 없음). backend 의 Java HttpClient 는 연결을 풀에 두고 다시 쓴다.
- **같은 실행 안에서도** 이어 쓴 연결의 전송 등이 새 연결보다 평균 0.5~1.3 s 짧았다 [계산]. 차이가 연결 맺기(1왕복)와 슬로 스타트 때문이라는 세부 기제는 [가설]이다.
- G0r 의 `DELETE` 는 31건 중 28건이 그 작업의 연결을 이어 썼다(약 1왕복).
- **8절의 `DELETE` 실패도 같은 줄기로 본다** [가설]: 풀의 연결을 서버가 막 닫았을 때 Java HttpClient 가 내는 오류 모양이다.
- **슬롯 시간은 부하에 따라 8.9~11.2 s 로 바뀐다** [계산].
  - S0(처리 + 2·h0)는 계획용 값이다. 다른 실행과 같은 정의(처리 + 넘김 중앙값)로 맞추면 G0r 슬롯은 약 11.2 s 다. 그래서 S0 와의 차이 중 약 0.3 s 는 정의 차이다.
  - 요청 λ 에 그 실행의 평균 슬롯을 곱하면 계획 ρ 0.5·0.7·1.3·1.65 가 0.44·0.65·1.03·1.28 이 된다. 잰 λ 까지 넣은 실제 ρ 는 0.48·0.74·0.91·1.19 다.
  - ρ0.7 은 도착이 요청보다 많아(250 대 219건/h) 실제 ρ 가 계획보다 컸다.
- **남은 확인**: uvicorn 유휴 시간을 늘려 G0 를 다시 재서, 연결을 이어 쓰면 전송이 실제로 줄어드는지 본다. 2026-11-19 3차에서 했다. 3차 Pod(2차와 다른 Pod)에서 5 s·75 s 를 같은 부하로 비교해, 75 s 에서 연결을 이어 써 전송 등 중앙값이 4.41 → 3.56 s 로 줄었다([2026-11-19_vm-3rd.md](2026-11-19_vm-3rd.md) 2절).

## 8. 남은 작업 폴더 — 정리 `DELETE` 실패

- **실패** [실험 결과]: `g3r13` 의 작업 `c5ca36f3`(11:17:45 생성, `queuedMs` 121 s·슬롯 대기 Wq 118 s)은 COMPLETED 였다. 그런데 11:19:59.867 UTC 의 정리 `DELETE /artifacts/c5ca36f3…` 가 실패했다: `java.io.IOException: HTTP/1.1 header parser received no bytes: the service keeps the job's files`.
- **흔적** [실험 결과]: 세션 backend 로그 전체(완료 540건)에서 WARN·ERROR 는 이 한 줄뿐이다. Pod 로그에는 이 작업의 `DELETE` 요청이 없다(`g3r13` 의 150건 중 이 1건만).
- **남은 폴더**: 15:29 UTC 에 Pod 볼륨의 `/workspace/beside-work/` 에 이 작업 폴더(25 MB)가 그대로 있었다(운영자 확인, 출력은 리포 밖).
  - backend 는 정리를 다시 시도하지 않는다.
  - 추론 서비스는 `DELETE` 에서만 작업 폴더를 지운다(`generation/inference_service/app.py` `delete_artifacts`). 오래된 폴더를 지우는 정리는 없다.
- **쌓이는 양** [계산]: 539건 중 1건(0.19 %, 95 % 구간 0.005~1.0 %, 표본 1건)이다. 같은 비율이 이어지고 폴더가 25 MB 라면, T3(3,600건/h)에서 시간당 약 7개(0.2~37개)·170 MB, 하루 약 4 GB(0.1~22 GB)가 네트워크 볼륨에 쌓인다.
- **고치는 방법 후보** [계획]:
  - `DELETE` 를 연결 오류에 한 번 다시 보낸다.
  - Pod 가 일정 시간 지난 작업 폴더를 지운다.
  - uvicorn 유휴 시간을 늘려 연결이 닫히는 때를 줄인다.
