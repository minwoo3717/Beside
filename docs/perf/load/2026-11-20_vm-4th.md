### 3차 가설 판정 (슬롯 2개의 내려받기)

- **확인한 것** [계산]:
  - c=2 에서 처리 평균은 8.09 → 9.86 s(+1.77 s)로 늘었다. 그중 +1.50 s 는 GLB 구간, +0.27 s 는 `MODEL_LOCK` 대기가 든 Pod 일이다(5절).
  - 슬롯 2개에서는 Pod 가 GLB 를 넘긴 뒤 VM 이 받아 저장할 때까지(GLB 구간, VM 저장 포함)가 길어졌다. 중앙값 1.75 → 2.29 s, p90 1.75~1.76 → 5.25 s 다.
  - 업로드 받기(1.356 s)와 Pod 의 응답(넘기기 약 15.5 ms, 답 → `GET` 0.274 s)은 c=1 과 c=2 가 같았다.
  - 그래서 내려받기에서 늘어난 시간은 Pod 가 GLB 를 다 넘긴 뒤에 쓰였다. Pod 가 늦게 답한 것이 아니다.
- **맞지 않은 것** [계산]: 3차 가설은 "동시 전송이 Pod 의 보내는 경로를 나눠 쓰고, 다른 작업의 추론·변환과 CPU 를 다툰다" 였다. 4차 조건(스레드 8, Pod CPU 한도에 걸린 주기 0)의 데이터는 이와 맞지 않는다.
  - 느린 GLB 구간은 tailnet 연결 하나(Pod 쪽 포트 55074, 74건, 중앙값 4.96 s)에 몰렸다.
  - 다른 연결(60838, 99건)은 900 s 까지 중앙값 1.75 s 였다.
  - 같은 연결 안에서는 겹침이 거의 상관없었다. 60838 에서 겹침 없음·다른 GLB 와 겹침·다른 추론/변환과 겹침이 모두 1.75 s 였다. 55074 에서 겹침 없는 구간은 4.95 s 였다.
  - Pod 의 tailscaled 는 내려받기 구간에 한 코어의 1.8~2.2 %(1초 창 최대 8.6 %)만 썼다. Pod CPU 한도에 걸린 주기는 0 이었다. 루프백 큐는 거의 비어 있었다.
  - 3차 G2r 은 기본 스레드로 CPU 한도에 287번(2.2 %) 걸렸다. 그래서 3차 조건의 CPU 다툼은 4차로 직접 가리지 못했다.
- **남은 것** [가설]:
  - 연결 하나가 왜 느려지는지는 모른다. 느린 것은 Pod → VM 방향뿐이다(업로드는 두 연결에서 같았다). 후보는 그 방향의 보내는 쪽(Pod 의 userspace tailscaled TCP), 받는 쪽(VM 커널 TCP 의 받는 창·JDK HttpClient 의 읽기), 또는 경로에 남는 연결별 혼잡 상태다.
  - c=1 의 연결 하나는 23분 내내 빨랐다. c=2 에서는 두 연결이 차례로 느려졌다. 연결이 두 개일 때만 생기는지는 이 데이터로 가리지 못한다.
  - 3차 `g2c2a`(다른 Pod·기본 스레드·JDK 유휴 1200 s)도 연결별로 갈렸다(처음부터 끝까지 중앙값 6.70 s·4.32 s, 0~300 s 에 이미 6.42·4.27 s) [계산]. 다만 두 연결 모두 같은 잣대의 3차 c=1(`g0ka75` 1.90 s)보다 처음부터 느렸다. 4차처럼 빠르던 연결이 도중에 느려진 모양은 아니고, 연결마다 수준이 정해져 끝까지 가는 점만 같다. 같은 기제인지는 [가설]이다.

### 같은 Pod 의 c=1 과 c=2

- 같은 Pod·같은 요청 λ 에서 c=2 의 용량은 c=1(415건/h)의 1.19배 이상이다(센 하한 495 ÷ 415) [계산].
  - 도착 − 기울기 추정(507~516건/h)으로는 1.22~1.24배, 가장 긴 포화 구간으로는 1.35배, 슬롯 시간 식으로는 1.63~1.66배다. 이 셋은 하한이 아니라 추정이다.
  - 3차의 약 1.3배(다른 Pod·다른 날·기본 스레드의 c=2 를 또 다른 Pod 의 c=1 과 비교)는 이 범위 안에 있다.
- c=2 의 처리 평균은 c=1 의 1.22배(9.86 / 8.09 s)였다. 3차·2차로는 1.60배(12.88 / 8.06 s)였다 [계산]. 다만 3차 `g2c2a` 는 다른 Pod·기본 스레드(CPU 한도에 걸린 주기 2.2 %)·JDK 유휴 1200 s, 2차 `g3r165` 는 또 다른 Pod·keep-alive 5 s·기본 스레드였다. 그래서 1.60 과 1.22 의 차이를 한 원인으로 돌리지 않는다.
- c=2 실행은 519건/h 에서 넘치지 않았다(포화 시간 27 %). 그래서 용량 범위가 넓다 [계산].

### 새 시작 기본값 (G0)

- 실제 Pod 의 `start_pod.sh` `[4/4]` 줄과 서비스 프로세스의 `/proc/<pid>/environ` 에 keep-alive 75 s·스레드 8 이 들어 있었다(`pod-session.txt`) [실험 결과].
- 3차 `g0th8`(같은 두 값을 손으로 넣음, 다른 Pod, JDK 유휴 1200 s)과 비교해 처리·추론·변환·전송 등의 중앙값이 0.05 s 안에서 같았다(k6 `load_waitMs` 중앙값은 +0.10 s) [계산]. Pod 는 달랐지만 GPU 종류(A40)와 G0 값이 같아 3차와 비교할 수 있다.
- S0 는 8.96 → 8.64 s 로 줄었다. 4차 G0 에 느린 작업이 없었기 때문이다(처리 최대 8.30 s, 3차 `g0th8` 14.01 s) [계산].
- backend HttpClient 유휴 60 s 아래에서 작업 연결 하나가 31건의 `POST`·`GET`·`DELETE` 를 모두 실었다. 이 연결은 k6 전의 운영자 확인 작업이 열었고, k6 구간 안의 새 연결은 0 이었다. 작업 사이 유휴 시간은 중앙값 21.9 s, 최대 23.8 s(확인 작업 뒤 첫 간격)로 60 s·75 s 보다 짧았다 [계산].

## 3. 슬롯 나누기 — Pod 요청별 시간 [실험 결과·계산]

**방법** (출력 `== 2.`):
- Pod 서비스는 HTTP 요청마다 `timing` 줄을 썼다. 칸은 `body_ms`(본문을 다 읽은 때), `start_ms`(응답 머리를 넘긴 때), `end_ms`(응답 본문 마지막 조각을 uvicorn 에 넘긴 때), `client`(tailscaled 가 연 루프백 포트), `at`(요청 머리를 읽은 UTC 시각)이다.
- `end_ms` 는 바이트가 Pod 를 떠난 때가 아니다. 1.3 MB GLB 는 소켓·tailscaled 버퍼에 다 들어간다. 그래서 GLB 의 전송은 VM 쪽 `finishedAt` 에서 `GET` 의 `at` + `end_ms` 를 빼서 구했다(GLB 구간).
- `finishedAt` 은 내려받기와 저장소 복사 뒤, `DELETE` 전에 찍힌다. 그래서 GLB 구간에는 VM 의 저장도 들어 있다.
- 작업과 맞추기: `GET`·`DELETE` 는 경로의 jobId 로, `POST` 는 응답 직전의 'upload mode' 줄로 맞췄다. 도착 순서로 맞춘 것과 세 실행 모두 100 % 같았다. 31·157·173건 모두 맞췄고 후보가 둘인 것은 없었다.
- 처리 시간에서 구간의 합을 뺀 값은 많아야 1 ms 였다.
- 시계: VM·Pod 둘 다 NTP 이고 시계 차는 재지 않았다. '섞임' 표시 구간은 그 차를 담는다. 앞 구간 + GLB 구간은 차가 서로 지워진다.
  - 앞 구간(약 0.15 s)이 한 방향 시간(새 연결 왕복 270 ms 의 절반, 약 0.135 s)과 비슷해 차는 작다고 본다 [가설].
  - Pod 로그를 읽어 붙인 시각은 0.2 s 마다 읽어 실제보다 늦다. 'upload mode' 줄은 `POST` 답보다 중앙값 0.09~0.11 s, 최대 0.27 s 늦게 찍혔다.

- **열림** [가설]:
  - tailnet 연결 하나가 어느 순간부터 느려지고 그대로 남는다. 기제는 모른다. 업로드(VM 이 보냄)가 두 연결에서 같았으므로 느린 것은 Pod → VM 방향이다. 그 방향의 보내는 쪽(Pod 의 userspace tailscaled TCP)인지 받는 쪽(VM 커널 TCP·JDK HttpClient)인지, 경로에 남는 연결별 혼잡 상태인지는 이 데이터로 가리지 못한다.
