작성 2026-11-18, 브랜치 `load/vm-1st`. [TRAFFIC_MODEL.md](TRAFFIC_MODEL.md) 의 A 시리즈(API 계층) 중 A0~A4 를 배포 VM 에서 처음 돌린 기록이다. 절차는 [deploy/loadtest/README.md](../../../deploy/loadtest/README.md), 스크립트는 [scripts/load/](../../../scripts/load/).

## 요약

GPU 생성을 뺀 API 계층(mock 워커, PROCESSING 60 s)을 2 vCPU·8 GB VM 에서 쟀다. 부하 발생기는 미국 서부의 Runpod CPU Pod 이고, 서울 VM 까지 왕복이 약 153 ms 다.

|---|---|---|---|
| A1 혼합 흐름 | 25 → 9,000명(T3 평상시 1,800명의 5배, 185 요청/s), 단계마다 8분 | 통과 단계 없음(drop 12, asset 전체 시간·서버 `uploadMs` 기준 미달) | 5xx·연결 오류 0, 폴링 p95 157~160 ms 로 변화 없음(p99 는 9,000명에서만 205 ms), VM CPU 단계 평균 최대 51 % |

- **먼저 한계에 닿는 것은 VM CPU(2 vCPU)이고, 그 CPU 를 가장 많이 쓴 것은 Spring 이 아니라 Caddy(TLS 종료·리버스 프록시)다** [실험 결과]. Caddy 를 병목으로 보는 것은 이 CPU 몫에서 나온 해석이다 [가설].
  - A2 900 요청/s 에서 Caddy 가 CPU 85~90 %(코어 하나 = 100 %)를 썼고, 1,200 요청/s 부터 132~143 % 를 썼다.
  - 같은 때 Spring 은 1분 창마다 poll 의 95 % 이상을 25 ms 이하로 처리했다(1,200 요청/s 의 1분 창 표본 3개만 25~50 ms).
- **Caddy 메모리는 A1 9,000명 유지 구간에서 2,170 MiB 였고, 부하가 멈춘 직후 드레인 중 2,246 MiB 까지 늘었다** [실험 결과]. 큰 업로드를 받은 연결이 끊길 때까지 버퍼를 잡는 것으로 보인다 [가설]. 실행 최대로 A3(업로드만)은 492 MiB, A4(내려받기만)는 167 MiB 였다.
- **TRAFFIC_MODEL §3 과 비교** [계산]:
  - T3 평상시(37 RPS)와 GPU 포화 때 폴링(약 300 RPS)에서 이 VM 은 서버 자원 기준(VM CPU 단계 평균 < 85 %·GC 뒤 힙 < 75 %·5xx 0)을 지켰다(A1 3단계 13.4 %·4.2 %, A2 300 요청/s 54.0 %·4.9 %). A1 은 drop 12 로 규칙상 통과 단계가 없고, 서버 `uploadMs` 기준은 아래처럼 판정하지 않았다.
  - T3 스파이크 + GPU 포화 최악값(약 921 RPS)은 A2 의 한계 바로 위다. 큐 상한(안건 #21) 없이는 여유가 없다.
- **GPU 계층** [계산]: exp-01 의 실제 처리 시간(T ≈ 10~16 s)으로 다시 계산하면 T2(공개 베타)는 GPU 1대로 되고, T3 는 15~23대가 필요하다(7절).
- **판정하지 못한 기준**: A1 에서 미달한 asset 전체 시간과 서버 `uploadMs`(TRAFFIC_MODEL §8)는 본문을 153 ms 경로의 새 연결로 주고받는 시간이 대부분으로 보여 [가설] 서버 한계로 판정하지 않았다. 같은 경로라도 연결을 다시 쓰는 A3 유지 구간에 만든 작업의 `uploadMs` p95 는 89~98 ms 였고 [계산, `vm/events.jsonl`], A4 의 asset 전체 시간은 10 /s 까지 기준 안이었다. 한국·일본 리전의 부하 발생기로 다시 잰다 [계획].
- **운영 보호**(백업·해시·조회 출력은 VM·개발 PC 에 있고 이 리포의 데이터 폴더에는 없다): 운영 데이터는 건드리지 않았다. 복구 뒤 운영 H2 sha256 이 백업 때와 같았고, `lt-` 작업 0건(`LT_JOBS = 0`), 공개 경로 시험 61개가 모두 통과했다.

### 1.1 부하 발생기를 개발 PC 에서 Pod 로 바꾼 이유 [실험 결과]

같은 날 새 TCP 연결로 `GET /api/v1/healthz` 를 300번 보냈다(`curl --connect-timeout 30`).

| 출발 | 파일 | 실패(응답 없음) | `time_connect` 중앙값 |
|---|---|---|---|
| 개발 PC(Windows curl, 02:45 UTC 무렵, 시각은 파일에 남지 않음) | `net-devpc-windows.txt` | 3 / 300 | 10.2 ms |
| VM 안(`--resolve` 127.0.0.1) | `net-vm-local.txt` | 0 / 300 | — |
| Runpod Pod(US-CA-2, 03:35 UTC) | `net-runpod.txt` | 0 / 300 | 154.5 ms |

- 개발 PC 의 실패 3건은 모두 TCP 연결이 맺어지지 않은 채(`time_connect` 0) 약 21 s 에 curl 종료 코드 28 로 끝났다. 개발 PC 의 WSL curl 시험에서도 실패가 있었지만 파일을 남기지 않아 인용하지 않는다.
- VM 호스트의 `ListenOverflows`·`ListenDrops`·`SyncookiesSent` 는 0 이었다(`nstat-start.txt`, 각 실행 `vm/nstat-end.txt`). 그러나 이것은 호스트 네트워크 이름공간의 값이고, Caddy 는 Docker 브리지 네트워크라 443 연결을 컨테이너 안에서 받는다. A1 동안 호스트 `TcpPassiveOpens` 는 98 늘었는데 k6 가 새로 맺은 연결은 약 8,000개였다 [계산: `http_req_connecting` 평균 × 요청 수 ÷ 154.5 ms]. 그래서 이 0 은 VM(Caddy) 쪽 연결 거부를 배제하지 못한다. 실패가 개발 PC 쪽 경로에서 생겼다는 것은 Pod·VM 안에서는 실패가 없었다는 데서 나온 추정이다 [가설].
- 개발 PC 에서 시작한 A0·A1 은 게임이 함께 돌아 버렸다(리포 밖 `discarded\`).
- 대가: 모든 요청에 왕복 약 153 ms 가 붙는다. 한국 사용자보다 훨씬 먼 경로다. 그래서 지연은 RTT_base 를 뺀 몫과 서버 쪽 지표로 함께 본다.

## 3. A1 단계형 혼합 흐름 [실험 결과]

`api_staged.js`, `ramping-arrival-rate`, 단계마다 증가 1분 + 유지 8분, `PRE_VUS=2000`. 03:40~04:54 UTC(74분). 데이터 `data/2026-11-18_1354-a1p1/`.

- 흐름은 사용자 수 ÷ 1,800 /s 로 건다. 순서는 healthz → POST(0.8 MB) → 2초 폴링 → asset(1.5 MB)다.
- 흐름의 5 %(`FAIL_RATIO` 0.05)에는 사진 이름으로 실패를 넣는다. 이 흐름은 FAILED → retry 1회 → 다시 FAILED 로 끝난다(실제 410 / 8,317).
- 이와 따로 healthz 만 부르는 browse 세션이 사용자 수 ÷ 450 /s 로 돈다(9,000명에서 20/s).

### 3.1 판정

- k6 종료 코드 99(기준 미달). 오류 기준으로 멈추지 않고 8단계(9,000명)를 끝까지 돌았다.
- **`dropped_iterations` 12 → TRAFFIC_MODEL §8 규칙대로 이 실행에는 통과 단계도 깨지는 지점도 없다**(k6 출력 `breaking point: invalid`).
  - k6 는 흐름 시나리오에 VU 2,000개(`PRE_VUS`), browse 시나리오에 5개(`api_staged.js` 고정값 `preAllocatedVUs: 5`)를 미리 만들었다.
  - 동시에 돈 VU 는 최대 349개라 흐름 쪽은 모자라지 않았다.
  - 유지 구간 요청 수를 예정 도착 수와 맞춰 보면, create 는 모든 단계에서 예정과 같고 healthz 는 7단계만 12건 모자란다(11,988 / 12,000). 따라서 버린 12개는 7단계의 browse 반복이다 [계산]. 시험 중에 더 만든 VU 도 12개다(`vus_max` 2,017 − 2,005).
  - **`PRE_VUS` 를 올려도 이 drop 은 없어지지 않는다.** browse 의 미리 만드는 VU 를 늘리는 스크립트 수정이 필요하다 [계획].
- k6 기준으로 그 밖에 실패한 것은 asset 전체 시간(p95 < 3 s 는 5~7단계, p99 < 6 s 는 1~7단계)뿐이다.
- TRAFFIC_MODEL §8 의 서버 기준 `uploadMs` p95 ≤ 300 ms 도 넘었다: 유지 구간마다 856~946 ms 였다(`vm/events.jsonl`, attempt 1·0.8 MB). 이 값은 k6 가 판정하지 않는다. asset 과 `uploadMs` 모두 본문을 153 ms 경로로 주고받는 시간이 대부분이라, 이 부하 발생기로는 판정할 수 없다 [가설].
- 1단계 asset 표본은 46건이라 p99 7.4 s 는 가장 느린 2건(약 7.3 s·7.5 s) 사이의 보간값이다.

## 7. exp-01 생성 시간으로 다시 계산 [계산]

exp-01([generation/experiments/2026-11-17_exp-01_baseline-runpod.md](../../../generation/experiments/2026-11-17_exp-01_baseline-runpod.md))의 값으로 T 를 정했다.

- Spring `processingMs` 10.3~13.4 s(표본 2건, Runpod A40, DERP 중계)를 T 의 하한으로 쓴다.
- GPU 슬롯은 `processingMs` 보다 조금 길게 잡힌다. 슬롯 안에서 먼저 부르는 `/healthz` 가 `queuedMs` 에 들어가기 때문이다(TRAFFIC_MODEL §9). 그래서 빈 큐 `queuedMs` 2.2~2.3 s 를 더한 12.5~15.7 s 를 상한으로 함께 넣었다.
- 명령: `python scripts/load/model.py --t 10.3 --t 12.5 --t 13.4 --t 15.7 --t 60`.

| T | GPU 1대 최대 | 1대 (ρ ≤ 0.7) | T2 필요 GPU | T3 필요 GPU | Q_max (c=1) |
|---|---|---|---|---|---|
| 10.3 s | 349.5건/h | 244.7건/h | 1 | 15 | 57 |
| 12.5 s | 288건/h | 201.6건/h | 1 | 18 | 47 |

- TRAFFIC_MODEL 의 표와 안건 #21 의 상한 값을 이 T 로 바꾸는 것은 exp-01 을 10건 이상으로 반복한 뒤에 한다 [계획].

  - Prometheus 는 Spring 만 읽는다. Caddy 가 직접 낸 오류·지연은 서버 쪽 데이터에 없고, k6 의 연결 오류·`http_req_failed` 로만 본다. Caddy CPU·메모리는 약 17 s 간격 `docker stats` 뿐이다.

  - k6 가드(서버 5xx·디스크로 멈추기)를 쓰지 않았다. 대신 사람이 Prometheus·`df` 를 보았다(5xx 0, 디스크 최대 사용 약 38 %(df 39 %, A2 — A1 업로드를 지우지 않은 채 시드를 더했다)).
