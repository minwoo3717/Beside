## P1 작업 목록 키셋 페이지 (v1 → v1p)

- **실패 사례**: `GET /api/v1/jobs` 는 작업이 쌓일수록 느려질 구조였다. 요청마다 모든 작업을 읽어 정렬하고, 커서는 목록을 처음부터 훑어 찾았다.
- **원인 가설**: 비용이 페이지 크기가 아니라 전체 작업 수(N)에 비례한다. 같은 이유로 목록을 부를 때마다 모든 Job 엔티티가 메모리에 올라온다.
- **개선**: `(createdAt desc, id desc)` 키셋 조회에 limit+1, `jobs(created_at, id)` 인덱스. 커서는 그대로 마지막 항목의 id(계약의 '불투명 문자열' 유지, `JobListPagingTest`).
- **비교 실험**: N≈390·1000·2000 에서 첫 페이지(limit 20) 각 100회, 중간 페이지(limit 100) 각 50회.
- **결과**: 첫 페이지 p50 이 N≈390 에서 11.4 → 5.4 ms(−53 %), N=1000 에서 10.7 → 4.2 ms(−61 %), N=2000 에서 13.1 → 3.6 ms(−72 %). 중간 페이지는 N=1000 에서 −16 %, N=2000 에서 −32 %. 최대 RSS 가 499 → 449 MiB(−10 %)로 준 것도 목록마다 전체 작업을 올리지 않게 된 결과로 본다(가설). 단건 조회·업로드는 차이 없음.
- **부작용 관찰**: 지연 0 인 mock E2E 흐름(`e2e_mock`)이 18.9 → 23.5 ms(+24 %, 악화)로 나왔다. 서버 쪽 처리 시간(events.jsonl totalMs)은 3~4 → 4~5 ms 로 1 ms 단위의 차이이고, 흐름 시간의 차이는 대부분 10 ms 폴링 간격에 걸리는 횟수(작업당 1.38 → 1.46회)에서 온다. 인덱스가 늘어 쓰기가 조금 느려졌다는 가설은 1 ms 해상도로는 확인되지 않는다. 앱의 폴링 간격(1초)에서는 보이지 않는 크기다.

## P4 썸네일을 202 뒤 백그라운드로 (v2 → v2p)

- **실패 사례**: 다음 버전 후보 v2 에서 업로드가 크게 느려졌다(v1 대비): 12 MP 사진 15 → 70 ms, 큰 사진 4장 136 → 366 ms, real 시나리오의 4.5 MB 사진 업로드 요청 43 → 272~278 ms, 12 MP 4스레드 동시 업로드 59 → 235 ms.
- **원인 가설**: 업로드 요청 안에서 첫 사진의 썸네일을 디코드했다. 디코드는 서버 전체에서 한 번에 하나라서 동시 업로드가 줄을 선다. 이 PC 에서는 실시간 백신이 갓 쓴 사진을 처음 열 때 검사해(4.5 MB 노이즈 PNG 첫 열기 216 ms, 다시 열면 1.3 ms) 그 대기도 요청에 들어간다.
- **개선**: 썸네일은 202 를 보낸 뒤 스레드 하나의 큐에서 만든다. `thumbnailUrl` 은 만들어지기 전까지 null(계약의 '없으면 null' 범위).
- **결과**: 12 MP 업로드 70.1 → 15.5 ms(−78 %), 동시 업로드 235 → 55 ms(−77 %), 큰 사진 366 → 139 ms(−62 %), real 업로드 요청 272~278 → 43~45 ms(−84 %), real·path 전체 흐름 285 → 87 ms(−69 %). 모두 v1 수준으로 돌아왔다.
- **같이 본 것**: 일은 사라진 것이 아니라 옮겨 갔다. 12 MP 시나리오의 서버 CPU 점유 시간은 v2 3.3 s, v2p 3.7 s 로 비슷하다(v1 은 1.7 s). 썸네일 큐가 뒤 측정에 섞이지 않도록 시나리오마다 서버가 쉴 때까지 기다린다(측정 방법). 그래도 흐름 안에서 백그라운드 디코드와 CPU 를 나누는 경우는 남는다: real 시나리오의 작업 사이 빈 시간(queueGapMs)이 6~18 → 11~23 ms 로 늘었다. 실제 GPU 추론은 수십 초라 무시할 크기다.

## P5 대기 순번 인덱스 (v2 → v2p)

- **실패 사례**: v2 에서 PENDING 작업 조회가 v1 의 2.6 ms 에서 4.9 ms(+88 %)로 느려졌다(작업 약 2,030개가 쌓인 DB).
- **원인 가설**: 폴링마다 대기 순번을 세는 `countQueuedBefore` 가 작업 표 전체를 훑는다.
- **개선**: `jobs(status, queued_at, id)` 인덱스와 범위 조건, `job_runs(job_id)`·`(finished_at)`·`jobs(pet_id)` 인덱스.
- **결과**: 4.90 → 4.66 ms(−5 %, **차이 없음**). 가설이 맞지 않았다: N≈2,030 에서는 전체 훑기도 싸고, v1 대비 남은 +2 ms 는 다른 곳에 있다. 인덱스는 N 이 커질 때를 위한 것으로 남기되 효과는 이 측정으로 보이지 않았다고 적는다. 다음 확인은 아래 '남은 비용'.

## 이전 → 현재 (v0 → v1)

4b 배포 기반(prod 프로파일, 업로드 전송, GPU 감시·오프라인 대기, Discord 알림, H2 백업)을 더했지만 측정한 경로의 회귀는 없다: 기동, 메모리, 업로드, 동시 흐름, 폴링, 목록, real·path 모두 '차이 없음'. 지연 0 mock 흐름만 25.8 → 18.9 ms(−27 %, 개선)로 나왔는데 원인은 확인하지 않았다(작업당 폴링 1.52 → 1.38회).

## 측정에서 고친 것

- 대기 없이 잰 빠른 실행(커밋하지 않은 동작 확인)에서는 v2p 의 동시 E2E·폴링이 앞 시나리오의 썸네일 디코드와 CPU 를 다퉈 2~3배 느리게 나왔다. 시나리오마다 서버가 쉴 때까지 기다리고, 서버 CPU 점유 시간을 함께 남기도록 도구를 고친 뒤 이 데이터를 쟀다.
- 같은 PC 의 다른 프로그램(게임 클라이언트 등)이 고정한 CPU 를 차지해 서버가 멈추는 일이 있어 서버·스텁·부하 생성기를 보통 이상 우선순위로 띄웠다. 측정 도중 게임이 시작된 첫 실행(13:46)은 버리고, 게임이 끝나 3분 연속 조용해진 뒤 다시 쟀다. 이 데이터의 스위트 직전 배경 CPU 는 17~33 %(중앙 19 %).
- 기록해 둘 이상치: v1p 2회차의 real,prod 업로드 시나리오에서 워밍업 한 건이 약 3분 멈췄다(원인 미상). 측정 표본(흐름 20개)은 정상이지만 그 시나리오의 서버 CPU 점유 시간은 이상치다. 버린 첫 실행에서는 v2p 의 real 업로드 흐름 약 70개 중 1개가 COMPLETED 를 본 직후 에셋 409(PROCESSING)를 받았다. 이번 데이터(15 스위트)에서는 다시 나오지 않았다 — 원인 미상 **[계획]**.

## 하지 않은 개선과 이유

- 업로드 모드의 정리(`DELETE /artifacts`)를 추론 슬롯 밖으로(P2): 슬롯을 더 잡는 시간이 작업당 왕복 1회(루프백 수 ms, Tailscale 수십 ms)라 수십 초 걸리는 추론에 비해 작다. VM ↔ GPU PC 실측 뒤 다시 본다.
- 업로드 저장을 복사 대신 이동(P3): VM 의 Docker 에서는 Tomcat 임시 폴더와 저장소 볼륨이 다른 파일시스템이라 결국 복사다. 닫지 않던 입력 스트림은 코드 리뷰에서 고쳤다.
- GLB 의 ETag/304, 목록 기본 기간, 응답 압축: 상태 코드나 앱 동작이 바뀌어 계약 회의 안건이다.
