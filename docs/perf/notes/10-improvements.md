# 개선 사례와 버전 비교

이 장의 숫자는 **[실험 결과]** 다. 표와 그림, P1~P5 절의 숫자는 이 보고서의 데이터(2026-11-01 12:57~14:02, 버전 6개 × 3회 교차, 같은 PC)에서 나왔다. P6·P7 의 원인 분리는 같은 날 바로 앞의 A/B 측정(`data/2026-11-01_1239_ablation`, 12:39~12:57, 버전 5개 × 3회, mock 시나리오 다섯 개만)에서 나왔다. 두 실행의 숫자는 섞어 판정하지 않는다. p50 은 세 반복을 합친 표본의 중앙값이다. 판정은 앞 장과 같은 규칙(|Δ| ≥ 10 % 이고 반복별 범위가 겹치지 않을 때만)이다. 원인 설명 가운데 확인하지 않은 것은 '가설'로 적었다. 하루 앞의 실행(`data/2026-10-31_1434`, v0~v2p)도 같은 결론을 냈다.

## P1 작업 목록 키셋 페이지 (v1 → v1p)

- **실패 사례**: `GET /api/v1/jobs` 는 작업이 쌓일수록 느려질 구조였다. 요청마다 모든 작업을 읽어 정렬하고, 커서는 목록을 처음부터 훑어 찾았다.
- **원인 가설**: 비용이 페이지 크기가 아니라 전체 작업 수(N)에 비례한다. 같은 이유로 목록을 부를 때마다 모든 Job 엔티티가 메모리에 올라온다.
- **개선**: `(createdAt desc, id desc)` 키셋 조회에 limit+1, `jobs(created_at, id)` 인덱스. 커서는 그대로 마지막 항목의 id(계약의 '불투명 문자열' 유지, `JobListPagingTest`).
- **비교 실험**: N≈390·1000·2000 에서 첫 페이지(limit 20) 각 100회, 중간 페이지(limit 100) 각 50회.
- **결과**: 첫 페이지 p50 이 N≈390 에서 11.5 → 5.1 ms(−56 %), N=1000 에서 9.0 → 4.0 ms(−55 %), N=2000 에서 10.5 → 3.6 ms(−66 %). 중간 페이지는 N=2000 에서 18.5 → 11.1 ms(−40 %), N≈390·1000 은 차이 없음. 최대 RSS 가 514 → 450 MiB(−12 %)로 준 것은 목록마다 전체 작업을 올리지 않게 된 결과로 본다(가설). 단건 조회·업로드는 차이 없음.

## P4 썸네일을 202 뒤 백그라운드로 (v2 → v2p)

- **실패 사례**: 다음 버전 후보 v2 에서 업로드가 크게 느려졌다(v1 대비): 12 MP 사진 13.9 → 64.4 ms, 큰 사진 4장 124 → 341 ms, real 시나리오의 4.5 MB 사진 업로드 요청 40 → 257~267 ms, 12 MP 4스레드 동시 업로드 49 → 222 ms.
- **원인 가설**: 업로드 요청 안에서 첫 사진의 썸네일을 디코드했다. 디코드는 서버 전체에서 한 번에 하나라서 동시 업로드가 줄을 선다. 이 PC 에서는 실시간 백신이 갓 쓴 사진을 처음 열 때 검사해(4.5 MB 노이즈 PNG 첫 열기 206 ms, 다시 열면 1.4 ms) 그 대기도 요청에 들어간다.
- **개선**: 썸네일은 202 를 보낸 뒤 스레드 하나의 큐에서 만든다. `thumbnailUrl` 은 만들어지기 전까지 null(계약의 '없으면 null' 범위).
- **결과**: 12 MP 업로드 64.4 → 14.6 ms(−77 %), 동시 업로드 222 → 65 ms(−71 %), 큰 사진 341 → 127 ms(−63 %), real 업로드 요청 257~267 → 38~40 ms(−85 %), real·path 전체 흐름 269 → 81 ms(−70 %). v1 대비로는 모두 차이 없음.
- **같이 본 것**: 일은 사라진 것이 아니라 옮겨 갔다. 12 MP 시나리오의 서버 CPU 점유 시간은 v2 3.6 s, v2p 3.6 s 로 같다(v1 은 1.2 s). 썸네일 큐가 뒤 측정에 섞이지 않도록 시나리오마다 서버가 쉴 때까지 기다린다(측정 방법). 그래도 쉬지 않고 이어지는 요청에서는 백그라운드 디코드와 CPU 를 나눈다(아래 '남은 비용').

## P5 대기 순번 인덱스 (v2 → v2p)

- **실패 사례**: v2 에서 PENDING 작업 조회가 v1 의 1.96 ms 에서 4.35 ms(+122 %)로 느려졌다(작업 약 2,030개가 쌓인 DB).
- **원인 가설**: 폴링마다 대기 순번을 세는 `countQueuedBefore` 가 작업 표 전체를 훑는다.
- **개선**: `jobs(status, queued_at, id)` 인덱스와 범위 조건, `job_runs(job_id)`·`(finished_at)`·`jobs(pet_id)` 인덱스.
- **결과**: 4.35 → 4.48 ms(+3 %, **차이 없음**). 가설이 맞지 않았다: N≈2,030 에서는 전체 훑기도 싸다. 인덱스는 N 이 커질 때를 위해 남긴다. 실제 원인은 P7 에서 찾았다.

## P6 썸네일 유무를 메모리에서 (review/api-v1.1 bd06de6)

- **실패 사례**: v1 대비 v2p 에서 폴링 처리량 −26 %, 단건 조회 +40~42 %(N≈390·1000·2000), 목록 중간 페이지와 첫 페이지도 항목마다 약 0.1 ms 씩 느렸다.
- **원인 가설**: `JobResponse.thumbnailUrl` 이 응답마다, 목록이면 항목마다 `Files.isRegularFile(썸네일)` 을 부른다. v1 에는 없던 파일 시스템 호출이다.
- **확인**: 같은 PC 에서 파일 2,000개로 잰 호출 한 번의 시간(6회 반복): 있는 파일 97~100 µs, 없는 파일 104~106 µs, 결과 GLB 의 `File.length` 103 µs, 메모리 집합 0.5 µs. 항목당 증가와 같은 크기다. 실시간 백신의 파일 시스템 필터를 거치는 Windows 의 값이라 Linux VM 에서는 훨씬 작을 것으로 본다(가설, VM 측정은 [계획]).
- **개선**: 썸네일이 있는 jobId 집합을 메모리에 둔다. 시작할 때 폴더를 한 번 읽어 채우고 만들기·지우기로 유지한다. 파일을 내주는 `find()` 와 드문 retry 만 디스크를 보고 집합을 바로잡는다. 응답 값은 같다(있으면 URL, 없으면 null).
- **결과**(A/B, P6 만 더한 v2f1): 폴링 처리량 1,346 → 1,685 요청/s(+25 %), 단건 조회 N≈390·1000·2000 에서 0.71/0.65/0.53 → 0.54/0.50/0.43 ms(−19~−24 %), 목록 첫 페이지 −31~−47 %, 중간 페이지 −31~−45 %. 모두 개선이고, v1(1,725 요청/s, 0.55/0.49/0.44 ms)과 같은 수준이다. PENDING 조회와 E2E 흐름은 차이 없음.

## P7 PENDING 대기 순번 조회를 트랜잭션 하나로 (review/api-v1.1 668d7a3·87e3c75)

- **실패 사례**: PENDING 작업 조회가 v1 대비 +122~129 %. P5 인덱스로도 그대로였다.
- **원인 가설**(코드와 라이브러리 소스로 확인):
  - PENDING 응답마다 저장소 호출 두 번(`findProcessingStartedAt`, `countQueuedBefore`)이 각자 세션과 커넥션을 연다(`spring.jpa.open-in-view=false`).
  - Spring Data JPA 3.2.0 은 `@Query` 문자열을 호출마다 ANTLR 로 다시 파싱한다(`QueryEnhancerFactory.forQuery` → `HqlQueryParser`; 정렬이 없어도 `renderSortedQuery` 가 파싱한다).
  - 앞 보고서의 '예상 시간 중앙값 질의(5초 캐시)' 는 틀렸다: 캐시는 60초이고, 측정 구간에서는 첫 워밍업 한 번만 돈다.
  - pending_poll 은 재시작 직후의 서버에서 워밍업 20회 뒤 200회를 잰다. 반복을 네 토막으로 나눈 중앙값(앞 실행)이 v1 3.3 → 1.8 ms, v2p 7.2 → 3.0 ms 로 내려가, JIT 전 코드에서 차이가 커진다(첫 50회 +3.9 ms, 마지막 50회 +1.3 ms).
- **개선**: 같은 JPQL 두 개를 `EntityManager` 로, 한 읽기 전용 트랜잭션 안에서 실행한다(저장소 조각 `JobQueueQueries`). 대기 중 조회 한 번의 세션 2 → 1(`QueueSnapshotTest`), ANTLR 재파싱 없음. 두 조회의 순서와 READ COMMITTED 의미는 그대로라 `ahead` 값도 같다.
- **비교 실험**(A/B): P6 만 넣은 v2f1 → 트랜잭션만 더한 실험 커밋 v2tx(`outlook` 에 `@Transactional(readOnly)`, `@Query` 경로 그대로) → P7 의 v2q.
- **결과**:
  - 트랜잭션만(v2f1 → v2tx): PENDING 3.37 → 3.78 ms(+12 %, 차이 없음). 세션·커넥션을 하나로 묶는 것만으로는 효과가 없었다(가설 반박). 오히려 목록 중간 페이지(N≈390 +17 %)와 지연 0 mock 흐름(+17 %)이 악화했다: `outlook` 전체에 트랜잭션을 걸면 끝난 작업의 응답에도 트랜잭션이 생긴다.
  - `@Query` 경로를 뺀 것(v2tx → v2q): PENDING 3.78 → 2.81 ms(−26 %, 개선). P7 의 몫은 ANTLR 재파싱을 포함한 Spring Data 문자열 쿼리 경로에서 나왔다(확인).
  - 합계: A/B 에서 v2r → v2q 4.10 → 2.81 ms(−31 %, 개선), 이 보고서의 실행에서 v2p → v2q 4.48 → 3.40 ms(−24 %, 개선).
- **남은 차이**: v1 대비 A/B 에서 +30 %(범위가 겹쳐 차이 없음), 이 실행에서 +74 %(악화). v1 은 대기 순번을 계산하지 않으므로 조회 두 개는 기능의 비용이다. 재기동 직후를 재는 시나리오라 실행마다 흔들림도 크다.

## 이전 → 현재 (v0 → v1)

4b 배포 기반(prod 프로파일, 업로드 전송, GPU 감시·오프라인 대기, Discord 알림, H2 백업)을 더했지만 측정한 경로의 회귀는 없다: 기동, 메모리, 업로드, 동시 흐름, 폴링, 목록, real·path 모두 '차이 없음'. PENDING 조회만 2.36 → 1.96 ms(−17 %, 개선)로 나왔는데 원인은 확인하지 않았다.

## 원인을 찾은 방법과 한계

- 다섯 경로(COMPLETED·PENDING 조회, 목록, 작은 업로드, 202 뒤 백그라운드)를 v1·v2p·tip 코드로 대조했고, 다른 검토자가 주장마다 반박을 시도했다. 그 결과 '목록 항목마다 N+1 조회'(업로드 목록은 JSON 열 하나), '완료된 작업도 대기 순번 계산'(COMPLETED 는 바로 없음) 같은 가설은 버렸다.
- JFR 프로파일은 이 PC(JDK 17.0.20, Windows)에서 Java 실행 표본(jdk.ExecutionSample)이 거의 잡히지 않아(요청 스레드 CPU 수 초에 표본 0~수십 개) 시간 분해에 쓰지 못했다. 대신 의심 호출의 마이크로벤치와, 의심 부분만 바꾼 커밋의 A/B 측정으로 확인했다(`versions-ablation.json`).
- e2e_mock 의 p50 은 첫 폴링에 끝나는 흐름의 비율이 바뀌면 10 ms 폴링 간격만큼 뛰는 문턱 효과다(앞 실행에서 첫 폴링 완료 v1 61 %, v2 83 %, v2p 35 %). 작업당 폴링은 이 실행에서 v1 1.48 → v2p 1.64 → v2q 1.66회다.
- A/B 실행은 앞 시나리오(기동·업로드)를 건너뛰어 e2e_mock 이 식은 서버의 첫 측정이 되므로, 절대값(v1 33 ms)이 이 보고서(21 ms)보다 크다. 같은 실행 안에서만 비교한다. A/B 에서 v2f1 → v2q 의 scale 업로드가 +19~32 %(악화)로 나왔지만 업로드 경로는 바뀐 코드가 없고 반복 범위도 넓어(n=90) 잡음으로 본다. 이 보고서의 실행에서는 v2p → v2q 업로드가 모두 차이 없음이다.

## 측정에서 고친 것

- 대기 없이 잰 빠른 실행(커밋하지 않은 동작 확인)에서는 v2p 의 동시 E2E·폴링이 앞 시나리오의 썸네일 디코드와 CPU 를 다퉈 2~3배 느리게 나왔다. 시나리오마다 서버가 쉴 때까지 기다리고, 서버 CPU 점유 시간을 함께 남기도록 도구를 고친 뒤 쟀다.
- 같은 PC 의 다른 프로그램이 고정한 CPU 를 차지해 서버가 멈추는 일이 있어 서버·스텁·부하 생성기를 보통 이상 우선순위로 띄운다. 게임이 켜진 동안에는 재지 않았다.

## 하지 않은 개선과 이유

- 업로드 모드의 정리(`DELETE /artifacts`)를 추론 슬롯 밖으로(P2): 슬롯을 더 잡는 시간이 작업당 왕복 1회(루프백 수 ms, Tailscale 수십 ms)라 수십 초 걸리는 추론에 비해 작다. VM ↔ GPU PC 실측 뒤 다시 본다.
- 업로드 저장을 복사 대신 이동(P3): VM 의 Docker 에서는 Tomcat 임시 폴더와 저장소 볼륨이 다른 파일시스템이라 결국 복사다. 닫지 않던 입력 스트림은 코드 리뷰에서 고쳤다.
- 결과 GLB 크기를 완료 때 저장(`asset.bytes` 의 `File.length` 제거, 항목당 약 0.1 ms): v1 에도 있던 비용이라 이번 회귀의 원인이 아니다. 열 추가와 retry 처리가 필요해 **[계획]**.
- 썸네일 일 줄이기(EXIF 읽기 생략, JPEG writer 재사용), 생성 시 merge SELECT 없애기(`Persistable`), 완료마다 다시 읽는 중앙값을 증분으로: 효과를 재지 않았거나 회귀와 무관해 **[계획]**.
- GLB 의 ETag/304, 목록 기본 기간, 응답 압축: 상태 코드나 앱 동작이 바뀌어 계약 회의 안건이다.
