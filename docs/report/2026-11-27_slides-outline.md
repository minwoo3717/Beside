# 발표 슬라이드 초안 — 장별 내용 (2026-11-27)

[CHECKLIST](../CHECKLIST.md) M15(슬라이드, 전원)의 초안이다. 장마다 내용을 적었다. 2026-11-27 에 이 내용으로 claude.ai Slides 덱 초안(리포 밖·비공개)을 만들었다. 같은 날 사용자 요청으로 11-06 발표 자료(Beside_v9)의 형식과 이미지 위주 구성으로 바꿨다: 18장(목차·동작·시연·감사 장 추가), 글은 발표자 메모로 옮김, 그림은 v9 이미지·운영 GLB 브라우저 렌더·측정 원자료로 그린 차트. 팀에 공유하고 검토하는 것은 [사람]이다.

- **흐름**: 문제 → 왜 → 구현 → 실험 → 결과 → 개선. 루트 CLAUDE.md 의 흐름(문제 → 구현 → 실험 → 결과 → 개선)에 멘토링(2026-11-25)의 '모든 작업에 왜' 를 더한 것이다. 이 흐름으로 갈지는 팀 결정 전이다 [사람].
- **숫자**: 모두 [발표 수치와 측정표](2026-11-27_measurements.md)(이하 '측정표')나 [최종보고서](최종보고서.md)에 있는 값이다. 새로 잰 것은 없다. 장마다 '출처' 줄의 번호는 측정표 '발표 수치 한 장' 의 번호다.
- **표기**: [실험 결과]·[계산]·[제안값]·[가설]·[계획] 은 측정표와 같다. 발표 화면에는 표기를 작게 남긴다(안 한 것을 한 것처럼 보이지 않게).
- 장 수는 14장(약 12~15분)을 가정했다. 발표 시간은 확인 전이다(CHECKLIST M1 [사람]).

## 1. 표지

- 제목: Beside — 사진 몇 장으로 만든 반려동물 3D, AR 로 곁에
- 팀 Beside, 중앙대 소프트웨어학부 캡스톤. 트랙: Backend(Spring) / 3D Generation(AnimalLift) / Unity AR

## 2. 문제

- 핵심 한 줄: 반려동물 사진 몇 장으로 그 동물을 3D 로 재현하고, 휴대폰 AR 로 곁에 두고 싶다.
- 어려운 점:
  - 사진 → 3D 생성에는 GPU 가 필요하고 오래 걸린다.
  - 결과를 앱이 바로 쓸 수 있는 파일(GLB)로 넘겨야 한다.
  - 여러 사람이 동시에 쓰면 GPU 앞에 줄이 생긴다.
- 출처: 최종보고서 1절
- 그림 제안: 사진 1장 → 3D 강아지 → AR 화면, 세 칸

## 3. 목표와 기준 (왜 이 기준인가)

- 목표:
  - MVP 전체 흐름(갤러리 → 업로드 → 폴링 → GLB → AR 배치)
  - 3D 품질 6항목(얼굴·귀·체형·털 색·무늬·번짐)
  - 수치 측정(생성 시간·GPU 메모리·크기·앱 로딩·FPS)
- 왜: 멘토·교수 피드백이 '쏘카 수준 트래픽 목표', '부하·장애 시험도 배포 환경에서' 였다. 그래서 트래픽 목표 T3(피크 생성 3,600건/h)를 가정으로 세우고 실제 배포에서 쟀다 [가정·파생].
- 출처: 최종보고서 1절, [TRAFFIC_MODEL](../perf/load/TRAFFIC_MODEL.md) 1~3절

## 4. 시스템 구성

- Unity Android 앱(ARCore, glTFast) ↔ Spring Boot 공개 API(GCP VM, 서울) ↔ Python 추론 서비스(Runpod A40, 스웨덴, Tailscale 사설망)
- 앱은 Spring API 계약 v1 만 본다. Python 은 내부 전용 `POST /infer` 다.
- 왜 Spring 과 Python 을 나눴나:
  - GPU 기계는 쓸 때만 켠다(비용). 그래서 작업 상태·저장·서빙은 항상 켜 둔 VM 이 맡는다.
  - 이 설명은 팀 확인 전이다 [사람] (CHECKLIST, 멘토 대응 문서의 '왜' 항목).
- 그림 제안: [ARCHITECTURE.md](../ARCHITECTURE.md) 의 mermaid 그림

## 5. 구현 ① 생성 파이프라인

- 대표 사진 검사·전처리: 개/고양이 1마리, 해상도·밝기·선명도 검사 → 크롭·배경 제거(ONNX).
  - 왜: AnimalLift 는 동물이 없는 사진에도 강아지를 낸다 [실험 결과]. 그래서 업로드 단계에서 거절한다.
- AnimalLift → GLB 변환 → 털 맵을 GLB 안에(`extras.beside`) → 리깅(템플릿이 있을 때) → 클립 5개
- 왜 AnimalLift 인가:
  - 같은 GPU(RTX 4060 Ti)에서 1장당 SF3D 0.67 s, TripoSR 1.63 s, AnimalLift 5.31 s 로 가장 느리다.
  - 그래도 고정 토폴로지(정점 4,310)와 털 정보를 주는 것은 AnimalLift 뿐이다. 그래서 리깅·털에 쓸 수 있다 [실험 결과].
- 출처: 최종보고서 1절·3절

## 6. 구현 ② 실제 서비스처럼 운영

- 배포: GCP VM + Caddy(HTTPS) + Docker Compose. 계약 v1 과 계약 테스트.
- 관측:
  - Prometheus·Grafana(지표 5종, API·추론 p50·p95 상시 그래프), Loki(로그), Tempo(트레이스)
  - 알림 13개 → Discord [적용]. 2026-11-27 18개(수집기 감시·GPU Pod 오류 포함) [구현됨, 적용은 배포 창 3]
  - 요청 id `X-Request-Id` 로 앱 → 서버 → GPU 를 한 줄로 찾기. 2026-11-27 부터 앱 흐름 id = trace id 라 업로드·작업·추론 단계가 한 트레이스, 앱 오류 화면의 '문의 번호'로 찾는다 [구현됨]
  - 제품 지표: 화면·버튼 이벤트 15종, 세션 퍼널·이탈 직전 화면·이탈 사유·불러오기 퍼널·작업 완료율(/admin) [구현됨]
- 보호: 큐 상한(19건, 503 `QUEUE_FULL`) [구현됨, 운영은 꺼 둠], VM 감시 자동 재시작, 5분 백업 → VM 밖 버킷
- 왜: 멘토링이 '감지가 빨라야 원인을 빨리 찾는다', '실제 제품처럼' 이라고 했다.
- 출처: 최종보고서 3절, [REDUNDANCY](../ops/REDUNDANCY.md) 3절

## 7. 실험 ① 한 건은 몇 초인가

- `inferMs` 중앙값 **3,761 ms**. A40, 사진 1장 반복 539건 [실험 결과] — 출처 1
- 한 건 처리 `processingMs` 중앙값 **8.09 s**. 그중 전송 등이 3.64 s 다 [실험 결과·계산] — 출처 2
  - 문제 → 개선: Pod keep-alive 5 s → 75 s 로 9.09 → 8.22 s(다른 실행) [계산]
- 발표자 메모:
  - '전송 등이 추론만큼(둘 다 3.64 s) 걸린다' 가 메시지다. 처음 적은 '추론보다 전송이 길다' 는 측정표(`inferMs` 3.64 s = 전송 등 3.64 s)와 맞지 않아 고쳤다.
  - 그 원인을 서울 VM ↔ 스웨덴 GPU 왕복(4차 ping 269 ms)으로 보는 것은 [가설] 이다.

## 8. 실험 ② API 는 얼마까지 버티나

- mock 워커로 API 계층만: 폴링 **900 요청/s 유지, 1,200 요청/s 에서 무너짐** [실험 결과] — 출처 4
- 먼저 닿는 한계는 VM CPU(2 vCPU)다. 그 CPU 를 가장 많이 쓴 것은 Caddy(TLS) 다. Caddy 가 병목이라는 해석은 [가설] 이다.
- 조건: 부하 발생기가 미국 서부라 왕복 약 153 ms 가 들어 있다. 1회 실행이다.

## 9. 실험 ③ GPU 앞의 줄 — 큐 상한

- A40 1대 처리 용량 **409건/h**(S_busy 8.81 s) [실험 결과·계산] — 출처 3
- 상한이 없을 때(과부하): 만든 383건 중 **132건(34.5 %)** 이 600 s 를 기다리다 클라이언트에서 끝났다.
- 상한 19 일 때: 337건 중 **51건(15.1 %)** 을 바로 503 으로 돌려보냈다. 받아들인 286건은 모두 완료됐고, 최대 176.3 s 걸렸다 [실험 결과·계산] — 출처 5
- 두 실행의 도착률이 달라(575 대 505.5건/h) 같은 조건의 짝은 아니다. 운영에서 켜는 것은 [계획] 이다.
- 그림 제안: 두 막대(상한 0 / 19)에 '오래 기다리다 실패' 와 '바로 거절 + 모두 완료' 를 나란히

## 10. 실험 ④ 일부러 고장 내 보기

- 실제 배포에서 장애 18가지를 재현했다(2026-11-20).
- 결론: **가장 위험한 장애는 감지되지 않는 장애였다** [실험 결과] (최종보고서 4.3).
- 대응 전 → 뒤 [실험 결과·계산] — 출처 6

## 11. 실험 ⑤ 서버가 통째로 바뀌어도

  - 끊김 **65 s**, 되돌리기 **63 s**. 목표 ≤ 3분 [제안값] 안이다.
  - 마지막 백업 뒤에 만든 작업까지 남았다(RPO 0).
- 훈련에서 찾은 것 4가지 중 셋을 고쳤다 [구현됨, 다음 전환으로 확인 전]:
  - 전환 때 최신 백업 zip 복사
  - 원본 대기열 검사
  - backend 정지가 10 s 를 넘어 강제 종료(SIGKILL)되던 것. 고친 뒤 정지는 0.66~0.72 s 다(개발 PC 3회 [실험 결과], 운영 VM 은 배포 전) ([backend-stop](../ops/2026-11-27_backend-stop.md)).
- 남은 하나(Grafana 알림 상태가 VM 마다 따로임)는 [계획] 이다.
- 그림 제안: 1초마다 healthz 를 찍은 점그래프(초록 200 / 빨강 502 구간 65 s). 원자료는 [probe-outages.csv](../ops/data/2026-11-26_failover-drills/probe-outages.csv)
