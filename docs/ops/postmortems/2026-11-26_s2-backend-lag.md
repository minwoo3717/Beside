### 1. 왜 (가설과 사용자 영향)
- **가설**: backend 앞(Caddy ↔ backend) 네트워크가 느려지면 Spring 이 재는 응답 시간에는 보이지 않는다. 그래서 알림도 없다. 앞단(Caddy) 로그에만 보인다.
- **사용자 영향**: 앱 폴링·업로드가 수 초~수십 초 걸린다.
- **배경**: 1차 부하 시험의 A2 붕괴(1,200 요청/s)도 Spring 쪽 p95 는 95 % 가 25 ms 안이었다.

### 2. 주입과 부하
- 부하: `api_staged.js USERS=9000 ABORT_ON_ERRORS=0`. S1 에서 폴링 p95 10.6 ms 로 건강했던 수준이다.
- 주입: backend 컨테이너의 veth 에 `tc qdisc add ... netem delay 200ms 50ms`(s2a·s2b)와 `500ms 100ms`(s2c·s2d)를 넣었다. `systemd-run --on-active` 로 자동으로 되돌렸다.

### 4. 감지
- **고치기 전**: 감지가 없었다. Spring 기반 규칙은 라벨이 틀렸고, 고쳐도 센 지연에서는 Spring 이 정상이라 울릴 수 없다.
- **고친 뒤**: 앞단 알림이 3분 35초에 왔다. 구성은 기준 1 s 를 넘는 데 약 1분, 지속 2분, 평가 간격 1분이다.

### 5. 영향
- 앞단 p95 최대 17.8 s(s2c)·17.3 s(s2d).
- k6 오류는 거의 없었다. 무너진 모양은 지연이다.

### 6. 원인
- **[실험 결과]** 주입한 netem. Spring 은 요청이 Tomcat 에 들어온 뒤만 잰다.
- **[가설]** 지연이 걸린 동안 연결이 Caddy 앞에 쌓여 앞단 지연이 수십 배가 된다. 풀린 순간 밀린 요청이 Spring 에 몰려 그때 Spring 지표가 튄다.

### 7. 완화와 영구 조치
- 그 자리: 주입을 걷어 냈다(자동 해제).
- 영구 조치(PR #35, [구현됨]): 조회 알림 고침, 앞단 지연 알림(12번째 규칙), SLO 에 '앞단 응답' SLI.
- 배포 전 검토(2026-11-26)에서 앞단 알림을 작업 조회만 보도록 좁혔다. 재시험(3분 35초)은 모든 요청을 보던 판으로 쟀다. 좁힌 판은 운영에서 [계획]으로 확인한다. 위 시간 순서의 앞단 p95 값은 처음부터 작업 조회만 잰 값(`s2_probe.py`)이다.

### 8. 재시험
s2d 에서 앞단 알림이 3분 35초에 왔다.

### 9. 잘된 것 / 아쉬운 것
- **잘된 것**:
  - Loki 로 모은 Caddy 로그가 Spring 이 못 보는 지연을 보여 줬다(멘토링의 '로그를 서버로').
  - 고장 난 규칙을 운영에 들어가기 전에 찾았다.
- **아쉬운 것**:
  - 실행 사이 정리가 섞였다(잘못 넣은 지연 18초, s2c 마무리와 s2d 시작이 겹침).
  - 실행마다 1회다.
