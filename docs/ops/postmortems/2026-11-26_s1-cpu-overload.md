### 1. 왜 (가설과 사용자 영향)
- **가설**: Caddy 는 2 GiB 상한(R5, 다시 잰 적 없음)에서 A1 을 9,000명 넘게 올리면 OOM 으로 다시 시작하거나 GC 에 묶인다.
- **사용자 영향**: 모든 연결이 잠깐 끊기거나 응답이 느려진다.

### 2. 주입과 부하
- 주입은 없다. 부하만으로 터뜨린다.
- `api_staged.js USERS=5400,9000,12600,18000 RAMP_S=60 HOLD_S=240 ABORT_ON_ERRORS=0`

### 4. 감지
- **첫 알림**: 18,000명 유지 시작 1분 42초 뒤의 대기열 알림이다. 사람이 지켜보기 전에 왔다.
- **울렸어야 했는데 안 울린 것**: '조회 응답 p95 > 1 s 10분'. 규칙이 Spring 에 없는 라벨(`uri="/api/v1/jobs/{id}"`)을 봐서 데이터가 비었다. 4분짜리 과부하에 10분 기준도 길다.

### 5. 영향
- k6 오류: 상태 0·4xx·5xx 모두 0.
- 18,000명 폴링 p95: 1,768.8 ms (9,000명 10.6 ms).
- 작업 실패는 일부러 넣은 5 % 뿐이다.

### 6. 원인
- **[실험 결과]** 2 vCPU 의 CPU 포화다. 메모리(OOM)가 아니다. 가설은 틀렸다.
- **[가설]** 흐름마다 2초 폴링과 0.8 MB 업로드를 18,000명 규모(흐름 10/s, 폴링 약 300/s)로 받으면, TLS(Caddy)와 backend 가 2 vCPU 를 넘는다.

### 7. 완화와 영구 조치
- **그 자리**: 큐 상한 19 를 켰다. 상한을 넘은 생성은 바로 503 을 받고, 폴링하는 흐름 수가 줄었다.
- **영구 조치**(PR #35, [구현됨]):
  - 조회 알림 라벨 `{jobId}`, 0.5 s·2분
  - 업로드 알림 5분
- **운영에서 상한 켜기**: `QUEUE_FULL` 을 아는 Unity 새 빌드 뒤에 한다(계획 그대로).

### 8. 재시험
- s1b 18,000명: 폴링 p95 206.3 ms(8.6배 줄어듦), 503 `QUEUE_FULL` 873건(의도), VM 부하 평균 약 11.
- 12,600명 단계는 앞 단계 없이 시작해 비교하지 않는다.

### 9. 잘된 것 / 아쉬운 것
- **잘된 것**: 대기열 알림이 사람보다 먼저 왔다. 상한을 켜는 대응이 바로 효과를 냈다. 스테이징이라 운영 영향은 0 이었다.
- **아쉬운 것**:
  - 응답 시간 알림이 망가져 있었다.
  - 작업 알림 14,781건이 알림 13건을 묻었다.
  - CPU 를 키우는 대응은 무료 체험 CPU 상한 때문에 비교하지 못했다.
