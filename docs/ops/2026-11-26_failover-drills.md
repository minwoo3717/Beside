- **고칠 길**: `failover_vm.sh` 0단계에서 대기열(`beside_jobs_queue`)이 0 이 아니면 경고하거나, 비워질 때까지 기다린다. → 2026-11-27: 0 이 아니면 멈추고(`BESIDE_ALLOW_QUEUE=1` 로 넘김), 읽을 수 없으면 경고만 한다 [구현됨]. 운영 DRY_RUN 에서 `ok: queue on beside-vm empty` 가 나왔다.

### 4. backend 가 10 s 안에 끝나지 않고 SIGKILL 로 죽는다

- **본 것**:
  - D-3 1단계(`compose stop backend`, 15:58:57.3 시작)에서 대기 VM backend 컨테이너가 15:59:09.08 에 종료 코드 137 로 끝났다. `OOMKilled` 는 false 다.
  - `backend/Dockerfile` 은 exec 형식(`ENTRYPOINT ["java", …]`)이라 JVM 이 SIGTERM 을 직접 받는다. compose 에는 `stop_grace_period` 가 없어 Docker 기본값 10 s 가 쓰인다.
  - 멈추는 동안 backend 로그는 한 줄도 없다.
- **영향**:
  - H2 가 정상으로 닫히지 않는다. 이번 사본은 행이 그대로 열렸지만, 강제 종료에 기대는 셈이다.
  - 배포(`deploy_vm.sh`)나 재시작 때도 같을 수 있다 [가설].
- **원인**: 무엇이 10 s 넘게 걸리는지는 모른다 [가설]. 후보는 종료 훅에서 기다리는 작업 실행기, 꺼진 Pod 로 가는 연결, 트레이스 내보내기 등이다.
- **고칠 길**: 2026-11-27 원인을 찾고 고쳤다 [구현됨] ([backend 정지 기록](2026-11-27_backend-stop.md)). 실행 중인 @Async 작업을 Spring 이 정지 단계 상한(기본 30 s)까지 기다린 것이 원인이다. 정지 신호로 기다림을 끝내고, 상한 5 s, compose `stop_grace_period: 30s` 를 두었다. VM 에서 종료 코드 143 확인은 배포 뒤 [계획].
