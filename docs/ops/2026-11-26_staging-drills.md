## S1 과부하 (A1 5,400 → 18,000명)

부하는 `scripts/load/api_staged.js` 이고, 단계마다 오르기 60 s 와 유지 240 s 다. 데이터는 [s1a](../perf/load/data/2026-11-25_1743-s1a/)(상한 0)와 [s1b](../perf/load/data/2026-11-25_1809-s1b/)(상한 19)에 있다.

| 단계 | s1a 폴링 p95 (k6) | s1b 폴링 p95 (k6, 상한 19) |
|---|---|---|
| 5,400명 | 9.1 ms | — |
| 9,000명 | 10.6 ms | — |
| 12,600명 | 41.9 ms | 300 ms (앞 단계 없이 0 에서 바로 올라 비교하지 않음) |
| 18,000명 | **1,768.8 ms** | **206.3 ms** · 503 `QUEUE_FULL` 873건(의도한 거절) |

- **어디가 무너졌나** [실험 결과]:
  - 18,000명 유지 동안 VM 부하 평균은 4 → 41 이었고, CPU 유휴는 0 %, 실행 대기 행렬은 18~20 이었다.
  - CPU 는 backend(java)가 85~117 %, Caddy 가 36~57 % 를 썼다.
  - 남은 메모리가 적어 커널 페이지 회수(kswapd)가 돌았다. backend 의 디스크 쓰기는 누적 5.8 GB(업로드 사진)였다.
  - Caddy 메모리는 단계마다 올랐다: 352 MiB → 1.17 GiB(9,000) → 1.14 GiB(12,600) → 1.52 GiB(18,000). 2 GiB 상한과 `GOMEMLIMIT` 1638 MiB 안에서 OOM 없이 버텼다.
  - k6 의 오류(상태 0·4xx·5xx)는 0 이었다. 무너진 모양은 오류가 아니라 지연이었다.
- **Spring 이 본 폴링 p95**(Prometheus, `http_server_requests`, 1분): 17:59 0.057 s → 18:00 0.53 → 18:01 0.98 → 18:02 1.12 → 18:04 1.96 s. 내부 CPU 포화는 Spring 지표에도 보인다.
- **감지** [실험 결과]:
  - 18,000명 유지는 17:59:05 에 시작했다. 📈 '대기 중 작업 19건 이상 5분' 이 18:00:47 에 도착했다.
  - '조회 응답 p95 > 1 s 10분' 은 울리지 않았다. 규칙이 Spring 의 실제 라벨(`/api/v1/jobs/{jobId}`)이 아니라 `{id}` 를 보고 있었다. 4분짜리 과부하에는 10분 기준도 맞지 않는다.
  - VM 감시 알림은 없었다(backend 는 healthy, 재시작 0).
- **대응과 재시험**:
  - RUNBOOK 대로 큐 상한(19, `Retry-After` 165)을 켜고 같은 부하로 다시 쟀다(s1b).
  - 18,000명에서 폴링 p95 가 약 8.6배 줄었고, 부하 평균은 약 11 이었다. 생성 요청 1,184건이 바로 503 을 받았다.
  - Grafana 알림: 18:12:48 📈 대기 p95 > 60 s(증설 기준), 18:15:47·18:17:48 ✅ 해제, 18:19:47 📈 대기열 19건(상한이 꽉 참).
- **함께 찾은 것**:
  - 훈련 동안 수집기가 받은 메시지는 14,781건이다. 대부분 작업 완료·실패 알림(📦 묶음 포함)이다.
  - 운영이었다면 팀 채널이 묻혀, 위의 Grafana 알림 13건을 찾기 어려웠을 것이다 [가설: 사람의 반응은 재지 않음].

## S2 backend 앞 지연 (A1 9,000명 + `tc netem` on backend veth)

backend 컨테이너의 veth 에 지연을 넣고, `systemd-run` 으로 자동 되돌리게 걸었다. 9,000명은 S1 에서 폴링 p95 10.6 ms 였던 건강한 수준이다.

| 실행 | 지연 | 넣은 시각 | 앞단(Caddy 로그) p95, 1분 | Spring p95 | 알림 |
|---|---|---|---|---|---|
| [s2a](../perf/load/data/2026-11-25_1823-s2a/) | 200 ±50 ms, 6분 | 18:26:25.9 | 0.04 → 0.25 → 0.37 → 0.83 → 1.02 s | 0.024 → 0.49 → 0.58 s | 없음(옛 규칙) |
| [s2b](../perf/load/data/2026-11-25_1835-s2b/) | 200 ±50 ms, 6분 | 18:38:19.2 | 0.04 → 0.25 → 0.33 → 0.46 s | 0.025 → 0.20 s | 없음(고친 조회 규칙 0.5 s 미달 — 맞는 동작) |
| [s2c](../perf/load/data/2026-11-25_1848-s2c/) | 500 ±100 ms, 4분 | 18:49:57.8 | 2.1 → 9.3 → 12.9 → 17.8 s | **0.024 그대로**, 풀린 뒤 2.45 s | 없음 |
| [s2d](../perf/load/data/2026-11-25_1856-s2d/) | 500 ±100 ms, 260 s | 18:58:08.5 | 1.35 → 8.1 → 11.5 → 17.0 s | **0.024 그대로**, 풀린 뒤 0.65 s | 📈 **앞단 응답 p95 > 1 s, 19:01:43.4 (3분 35초)** |

- **해석**:
  - 지연이 크면 Caddy 앞 연결이 쌓여 앞단 지연은 넣은 값의 수십 배가 된다.
  - Spring 은 요청이 Tomcat 에 들어온 뒤만 잰다. 그래서 지연이 걸린 동안에는 정상으로 보이다가, 풀린 순간 밀린 요청이 한꺼번에 들어와 튄다 [가설: 패킷 순서까지는 보지 않음].
  - 200 ms 에서는 Spring 도 일부 올랐다(0.58 s). 연결이 쌓이며 Tomcat 스레드 대기가 생긴 것으로 본다 [가설].
- **진단 경로**:
  - 앞단 알림 → Grafana 'Beside 로그' 의 Caddy 응답 시간은 높은데 'Beside 운영' 의 API p95 는 정상 → 원인은 backend 바깥(네트워크·Caddy)이다.
  - 이번 원인은 `tc qdisc show` 의 netem 이었다(주입이므로 자동으로 풀렸다).
- **대응**:
  - 앞단 지연 알림을 Loki 규칙으로 새로 만들었다. 기준은 Caddy 접근 로그의 `duration` p95 > 1 s, 2분이다.
  - 조회 응답 알림은 라벨을 `{jobId}` 로 고치고 기준을 0.5 s·2분으로 바꿨다.
  - 둘 다 스테이징 Grafana 에 바로 넣어 s2b·s2d 로 확인했다.
- **기록에 남길 섞임**:
  - 18:47:58~18:48:16 에 잘못 넣은 지연 18초가 있다. s2b 의 마지막 정리 구간이었다.
  - s2c 의 마무리와 s2d 시작이 몇십 초 겹쳤다. 남은 흐름이 적어 영향은 작다고 본다 [가설].
